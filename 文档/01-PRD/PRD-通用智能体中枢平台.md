## 2. 需求背景

当前仓库已经演化出两个独立产品形态：

1. `mission-control`：中心服务端，用于汇聚来自不同节点的智能体状态、会话信息与任务数据。
2. `mission-control-client`：本地客户端，用于监测当前机器上的智能体运行时、会话和本地配置，并通过桥接同步到中心端。

现阶段系统仍存在 OpenClaw 历史包袱，但目标已经明确转向“通用智能体中枢平台”，要求能够容纳和监测多个不同来源的智能体与会话系统，而不是只服务某一个特定框架。

## 3. 问题定义

当前系统面临以下核心问题：

1. 中心端与边缘端虽然已经分离，但职责边界、支持矩阵、扩展方式还需要通过正式 PRD 固化。
2. 多种智能体框架的接入策略不统一，部分框架是原生支持，部分框架仅存在字段级兼容，缺少统一扩展规范。
3. 本地检测能力已经覆盖 Claude、Codex、Hermes、OpenClaw，但对 Cursor、OpenCode、Antigravity 等未来目标还没有形成完整实施方案。
4. 研发过程缺少稳定的文档先行闭环，后续迭代难以快速续接。

## 4. 产品愿景

构建一个“去中心化执行、中心化监控与协调”的通用智能体中枢平台，使任意物理节点上的多类智能体都能以统一模型接入系统，实现可观测、可追踪、可调度、可扩展。

## 5. 产品目标

### 5.1 业务目标

1. 将中心服务端定位为统一的控制塔与汇聚层。
2. 将客户端定位为本机探针、状态采集器和边缘执行节点。
3. 让不同类型的智能体都能被统一映射到同一套 Agent 模型中。
4. 让后续新增框架能够以明确的扩展方式接入，而不是继续在代码中散落硬编码。

### 5.2 交付目标

1. 建立正式的文档先行研发流程。
2. 将当前产品能力、当前支持矩阵、后续演进路线沉淀为文档。
3. 为后续 Cursor、OpenCode、Antigravity 等框架接入预留设计入口。

## 6. 非目标

1. 本轮不要求立即完成 Cursor、OpenCode、Antigravity 的实际探测实现。
2. 本轮不要求重写现有全部服务端与客户端代码。
3. 本轮不要求一次性消除所有 OpenClaw 相关代码。

## 7. 用户角色

### 7.1 平台管理员

关注全局节点、全局智能体、跨节点任务、全局运行状态与系统配置。

### 7.2 节点运维者

负责某一台物理机器上的客户端部署、本地探测、运行时安装与桥接配置。

### 7.3 智能体操作者

关注具体 Agent、Session、任务执行、模型使用与异常排查。

## 8. 产品形态

### 8.1 中心服务端

主要职责：

1. 接收客户端桥接上报的 Agent 和 Session 信息。
2. 提供统一视图展示节点、智能体、任务、会话、成本与状态。
3. 维护统一的数据模型，包括 `framework`、`node_id`、`parent_id`。
4. 为后续跨节点调度、跨节点搜索、统一权限控制提供基础。

### 8.2 本地客户端

主要职责：

1. 监测本机智能体运行时安装状态。
2. 扫描本机 Agent 定义目录。
3. 扫描本机 Claude/Codex/Hermes 等会话数据。
4. 与中心端建立桥接连接，并持续上报状态。
5. 对 OpenClaw 类型保留本地 Provision 能力，对非 OpenClaw 类型优先做探测和会话聚合。

## 9. 核心场景

### 9.1 场景一：中心端汇聚多个客户端

平台管理员在中心端看到来自不同节点的 Agent 列表，并能依据节点、框架、父子层级进行查看和筛选。

### 9.2 场景二：客户端自动发现本机 Agent

客户端扫描本机 `~/.agents`、`~/.codex/agents`、`~/.claude/agents` 等目录，把发现的 Agent 定义写入本地数据库，并通过桥接同步到中心端。

### 9.3 场景三：客户端自动发现本机会话

客户端扫描本机 Claude Code、Codex CLI、Hermes、OpenClaw Gateway 会话，并将会话状态统一展示。

### 9.4 场景四：统一建模不同框架

所有 Agent 都具备统一基础字段，包括名称、角色、状态、节点归属、框架类型、父子关系、最近活动时间等。

### 9.5 场景五：后续接入新框架

当需要新增 Cursor、OpenCode、Antigravity 等探测能力时，开发应按统一扩展模型新增 detector、session parser、bridge payload、UI 显示与测试，不再使用散乱临时逻辑。

## 10. 功能需求

### FR-001 统一 Agent 数据模型

系统必须支持以下统一字段：

1. `framework`：区分 Agent 来源框架。
2. `node_id`：标识 Agent 所属客户端节点。
3. `parent_id`：标识 Agent 父子层级。
4. `status`：标识 Agent 当前在线状态。
5. `source`：标识数据来源，例如本地、桥接、网关等。

### FR-002 中心端桥接接入能力

中心端必须支持接收客户端桥接连接，并将上报的 Agent 状态写入中心数据库。

### FR-003 客户端本地探测能力

客户端必须支持：

1. 本地 Agent 定义扫描。
2. 本地运行时检测。
3. 本地会话扫描。
4. 上报桥接能力。

### FR-004 多框架兼容策略

系统必须区分三类框架接入方式：

1. 原生运行时型：如 OpenClaw、Hermes。
2. 本地会话型：如 Claude、Codex。
3. 外部适配器型：如 generic、langgraph、crewai、autogen、claude-sdk。

### FR-005 OpenClaw 条件化能力

系统必须仅在 `framework = openclaw` 时启用本地 Provision、网关工作区相关能力；非 OpenClaw 类型默认不走该路径。

### FR-006 可扩展性

系统必须为新增框架探测器、会话解析器和桥接 payload 保留统一扩展点。

## 11. 非功能需求

### NFR-001 可维护性

服务端和客户端职责必须明确，扩展新框架时应优先通过独立模块完成。

### NFR-002 可追踪性

每轮开发必须能通过文档恢复需求、设计、任务和验证结论。

### NFR-003 自托管友好

系统应延续当前轻依赖、自托管模式，避免引入不必要的外部基础设施。

### NFR-004 兼容演进

在去 OpenClaw 强绑定的过程中，需要保持当前 OpenClaw 用户的可用性。

## 12. 当前支持矩阵

### 已有较明确支持

1. OpenClaw
2. Claude Code
3. Codex CLI
4. Hermes
5. generic / langgraph / crewai / autogen / claude-sdk 适配器

### 已纳入目标但未完成一等支持

1. Cursor
2. OpenCode
3. Antigravity

## 13. 验收标准

### AC-001 文档先行闭环建立

本仓库必须建立完整的文档主目录和文档先行工作规范。

### AC-002 中心端与客户端定位明确

PRD、架构设计、程序设计与任务拆解文档中，必须明确中心端与客户端的职责边界。

### AC-003 当前支持能力被准确记录

文档必须准确区分当前已经支持的运行时/框架与后续目标支持项。

### AC-004 后续开发可直接续接

后续功能开发应能够直接在既有 PRD、测试、设计、任务、状态文档上继续推进，而不需要重新建立文档体系。

## 14. 后续演进方向

1. 建立统一 runtime detector 插件机制。
2. 为 Cursor、OpenCode、Antigravity 增加专用探测与会话解析能力。
3. 强化中心端 central mode，彻底区分“纯汇聚端”和“本地探测端”。
4. 增强跨节点搜索、跨节点调度、跨节点状态分析能力。
