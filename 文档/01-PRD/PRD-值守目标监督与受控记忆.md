## 2. 背景与问题

当前人工值守可以识别 Worker 等待确认并代发一条用户消息，但它仍是被动、单轮的“判官”：

1. 用户不能直接给值守 Agent 一个长期目标。
2. 值守 Agent 不能将目标拆成任务并分派给多个 Worker。
3. 值守只关注单次等待，缺少对计划、进度、产物、偏离和最终验收的持续监督。
4. 当前记忆只作为检索片段注入，尚未形成“结果反馈 → 经验候选 → 审核晋升 → 后续复用”的学习闭环。
5. 值守运行稳定性缺少统一指标，历史测试绑定的错误会污染当前启用绑定的判断。

本需求将值守 Agent 扩展为目标监督者。它不替代 Worker 执行业务，而是代表用户管理目标完成过程。

## 3. 产品目标

1. 用户可以向值守 Agent 提交目标、约束、预算、截止时间和验收标准。
2. 值守 Agent 将目标拆成可验证任务计划，并由中心服务校验后创建任务。
3. 值守 Agent 根据 Worker 能力、节点、在线状态和负载分派任务。
4. 系统持续监控任务和 Worker 会话，识别阻塞、偏离、超时和质量不足。
5. 值守 Agent 可以给 Worker 纠偏、重试、补充任务、换 Worker 或请求人工决策。
6. 目标必须经过独立验收后才能完成，并保留完整证据链。
7. 值守 Agent 可以积累受控记忆，逐步理解用户偏好、项目事实和有效方法。
8. 高风险操作、价值冲突和超预算行为必须转人工。

## 4. 非目标

1. 不把值守 Agent 作为普通任务执行者，`tasks.assigned_to` 不能指向 human-watch Agent。
2. 不允许值守 Agent 绕过权限请求、租户授权或高风险审批。
3. 不允许模型直接写数据库；模型输出必须经过中心服务结构化校验。
4. 不承诺完全替代人类。V1 只覆盖低/中风险、验收标准明确的监督工作。
5. 不允许一次对话直接形成永久记忆或自动修改安全策略。
6. V1 不做跨租户目标、跨租户记忆共享和无限自治循环。

## 5. 核心概念

| 概念 | 定义 |
|------|------|
| Goal | 用户希望达成的结果，包含验收标准、约束、预算和截止时间 |
| Goal Supervisor | 目标监督模式下的值守 Agent，负责计划、分派、监督、纠偏和收口 |
| Reactive Watch Session | 现有被动值守判官会话，用于回复 Worker 等待确认 |
| Goal Session | 同一值守 Agent 的独立目标管理会话，不与 Reactive Watch transcript 混用 |
| Plan Version | 每次目标拆解或重规划生成的不可变计划版本 |
| Goal Task | 复用现有 `tasks` 的执行任务，并通过关系表关联 Goal 和计划版本 |
| Supervision Event | 计划、分派、阻塞、纠偏、重试、验收等 append-only 事件 |
| Memory Candidate | 从结果中提取、尚未获准进入长期记忆的候选 |
| Long-term Memory | 经证据或人工审核后可被后续目标和值守判断检索的记忆 |

## 6. 角色与权限

| 角色 | 权限 |
|------|------|
| 用户/操作者 | 创建目标、确认计划、调整预算、暂停/取消、处理人工决策、验收结果 |
| 值守 Agent | 生成计划建议、分派建议、监督判断、低/中风险纠偏、验收建议、记忆候选 |
| Worker | 执行任务、汇报进度、提交产物、创建权限请求 |
| 中心服务 | 状态机、校验、任务落库、预算控制、审计、重试和权限强制执行 |
| Edge/托盘 | 运行值守/Worker CLI、会话读写、可靠消息执行和本地健康保障 |

## 7. MVP 范围

1. 单个目标最多 8 个任务、最多 3 个 Worker。
2. 初始计划默认需要用户确认后才能开始；可显式开启低风险自动执行。
3. 每个目标最多重规划 5 次，每个任务最多自动重试 3 次。
4. 默认最长运行 24 小时；超过截止时间或预算自动暂停并转人工。
5. 支持 Codex/Claude Worker；Worker 与值守可以在同一 Edge 节点，跨节点通过可靠消息分派。
6. 记忆候选默认人工审核；同类成功证据达到配置阈值后可自动晋升。

## 8. 用户流程

### 8.1 创建目标

用户选择值守 Agent，输入：

- 目标描述。
- 可验证的成功标准。
- 必须遵守的约束和禁止项。
- 截止时间、优先级、预算。
- 可用 Worker 范围。
- 初始计划是否需要确认。

系统创建 `draft` Goal，值守 Agent 生成结构化计划，中心校验后进入 `awaiting_plan_approval` 或 `running`。

### 8.2 计划与分派

每个计划任务必须包含：

- 标题、明确输入、预期输出。
- 验收标准。
- 依赖任务。
- 推荐 Worker 能力。
- 预计耗时和风险。

中心根据能力和负载选择 Worker，创建现有任务并建立 Goal 关系。Worker 通过任务队列或 Bridge 收到任务。

### 8.3 监督和纠偏

系统通过事件驱动加周期 watchdog 监控：

- 任务状态长期不变。
- Worker transcript 等待回复或权限。
- Worker 输出偏离目标或违反约束。
- 任务完成但产物缺失。
- 依赖失败、Worker 离线、Bridge 断开。
- 预计成本或时间即将超限。

值守 Agent只能提出结构化动作，中心按策略执行：继续、补充信息、纠偏、重试、换 Worker、补任务、重规划、转人工、暂停或终止。

### 8.4 验收和收口

所有任务完成后进入 `verifying`：

1. 独立验收上下文读取目标、成功标准、任务产物和测试证据。
2. 验收不得只依赖执行 Worker 的自报状态。
3. 验收通过进入 `completed`；不通过生成缺口任务或转人工。
4. 生成最终报告：完成内容、证据、偏差、风险、费用和记忆候选。

## 9. 功能需求

### FR-001 目标生命周期

状态机：

```text
draft -> planning -> awaiting_plan_approval -> running
running -> blocked | paused | verifying | failed | cancelled
blocked -> running | paused | failed
verifying -> running | completed | failed
```

所有状态变化必须写入监督事件，不允许直接无审计覆盖。

### FR-002 结构化计划

值守 Agent 输出 JSON 计划；中心必须校验任务数量、依赖无环、Worker 类型、风险、预算和验收字段。非法计划退回值守 Agent 修正，不得直接写任务。

### FR-003 Worker 选择

Worker 评分考虑：

- `agent_kind` 必须是可执行类型，不是 human-watch。
- framework/session kind 是否受支持。
- 能力标签和项目关联。
- 所在 `client_id` 与 Bridge 状态。
- 当前 in-progress 数、最近成功率和错误率。
- 用户限定的 Worker 白名单/黑名单。

### FR-004 任务分派

复用现有 `tasks` 和 task queue。Goal 只保存关系、依赖、验收和计划版本，不复制任务事实。任务创建必须带 `metadata.goal_id`、`goal_plan_version` 和 `acceptance_criteria`。

### FR-005 监督循环

事件到达时立即评估，watchdog 默认每 60 秒兜底。每个 Goal 同时只能有一个监督 lease，防止多实例重复纠偏。

### FR-006 纠偏动作

支持动作：

- `continue_worker`
- `request_progress`
- `correct_direction`
- `retry_task`
- `reassign_task`
- `create_followup_task`
- `replan_goal`
- `request_human_decision`
- `pause_goal`
- `fail_goal`

每次动作必须包含理由、依据、风险、幂等键和预期结果。

### FR-007 风险和预算

1. low/medium 可按策略自动执行。
2. high/critical、扩大范围、删除数据、外发信息、增加预算必须转人工。
3. 强制限制最大任务数、重试数、重规划数、运行时长、模型调用和估算费用。
4. 达到任一限制时进入 `paused`，不得机械回复“继续”形成无限循环。

### FR-008 独立验收

验收器只读取明确证据：任务结果、测试、文件/接口状态、用户确认。验收结果包含逐条成功标准的 pass/fail/unknown 和证据引用。

### FR-009 分层记忆

记忆类别：

- `preference`：用户偏好和默认选择。
- `fact`：项目、环境和约束事实。
- `episode`：一次目标或纠偏的过程和结果。
- `procedure`：经过验证的可复用方法。

每条记忆必须保存来源、作用域、置信度、状态、证据、有效期和冲突关系。

### FR-010 记忆晋升

1. Goal 完成、纠偏成功/失败、用户明确反馈时生成候选。
2. 候选默认 `pending_review`。
3. 用户确认或多次独立成功证据达到阈值后进入 `approved`。
4. 新事实与旧记忆冲突时创建 supersede 关系，不直接覆盖历史。
5. 低效果、过期或被用户否定的记忆降权、拒绝或过期。

### FR-011 记忆使用

检索顺序：当前目标/会话事实 > 项目事实 > 用户偏好 > procedure/episode。每次注入限制条数和字符数，并记录哪些记忆被使用及最终效果。

### FR-012 UI

值守 Agent 详情新增：

- 目标列表和创建入口。
- 目标状态、计划版本、任务 DAG。
- Worker 分派和当前进度。
- 监督事件、纠偏记录和人工决策。
- 验收证据和最终报告。
- 记忆候选、已批准、冲突、过期管理。
- 健康摘要和最近稳定性指标。

### FR-013 审计

计划、分派、纠偏、人工决策、验收和记忆晋升均必须 append-only 留痕，关联 `goal_id`、`task_id`、`agent_id`、`session_id`、`message_id` 和 `correlation_id`。

## 10. 指标与 SLO

| 指标 | MVP 目标 |
|------|----------|
| 可靠消息完成率 | >= 99%（排除主动取消） |
| 值守介入 P95 | <= 15 秒（Edge 在线） |
| 重复任务/重复纠偏 | 0 |
| 目标状态丢失 | 0 |
| 高风险自动执行 | 0 |
| 记忆无来源写入 | 0 |
| 单 runtime 监听 | 始终为 1 |
| 目标最终报告完整率 | 100% |

## 11. MVP 验收场景

1. 创建“检查并修复一个测试项目问题”的目标，值守拆成 3 个任务并分给 2 个 Worker。
2. 一个 Worker 等待确认，值守在 15 秒内基于目标和上下文回复。
3. 一个 Worker 输出偏离成功标准，值守发送纠偏指令并保留证据。
4. Worker 离线后任务重分派，原任务不重复执行。
5. 所有任务完成后，验收器发现一项缺口并生成补充任务，最终通过。
6. Goal 完成后产生记忆候选，未经批准不会进入长期记忆。
7. 第二个相似 Goal 能检索已批准 procedure，并记录其效果。
8. 全链路可通过 goal/task/message/correlation ID 追踪。

## 12. 发布策略

1. 仅测试租户和白名单值守 Agent 开启。
2. 默认要求计划人工确认，默认关闭记忆自动晋升。
3. 先完成单目标闭环，再开放多 Worker 并发。
4. 生产灰度前完成 72 小时单 runtime、Bridge、Mailbox 和值守 canary 观察。
