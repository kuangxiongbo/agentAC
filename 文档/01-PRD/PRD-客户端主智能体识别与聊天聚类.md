# PRD-客户端主智能体识别与聊天聚类

## 1. 文档信息

- 文档状态：草案
- 当前版本：V1.0
- 更新时间：2026-04-17
- 所属产品：`mission-control-client`
- 关联总需求：`文档/01-PRD/PRD-通用智能体中枢平台.md`

## 2. 背景

当前客户端已经具备部分本机运行时检测能力，并能聚合 Claude、Codex、Hermes、OpenClaw Gateway 的会话数据，但还存在以下问题：

1. 主智能体没有被统一建模为客户端中的顶层 Agent。
2. Agent 创建向导中的框架选项是写死的，不依赖本机真实安装结果。
3. 聊天会话列表按 `gateway/local` 粗分，不按主智能体类型分组。
4. 运行时安装、建智能体、任务分配与监测能力没有围绕主智能体形成统一入口。

用户希望先完成客户端侧能力，使客户端能把本机已安装的智能体运行时识别为“主智能体”，并以此为基础再创建子智能体；同时聊天页需要把所有主智能体会话按类型分类展示，并做到安装、发任务、建智能体、监测与管控一体。

## 3. 问题定义

### 3.1 主智能体缺失

已安装运行时和顶层 Agent 之间没有稳定映射，导致：

1. 用户无法直观看到本机有哪些主智能体。
2. 子智能体无法稳定挂靠到主智能体之下。

### 3.2 创建向导不受真实环境约束

当前向导允许用户选择未安装或未识别的框架类型，导致配置路径与本机实际能力脱节。

### 3.3 聊天列表缺少业务分类

当前会话视图虽然聚合了本地和网关会话，但没有从“主智能体类型”角度展示，不符合用户心智。

### 3.4 监测与管控割裂

当前客户端中，安装入口、主智能体监测、Agent 创建、任务分配和聊天会话没有共享同一套主智能体模型。

## 4. 目标

1. 客户端自动识别本机已安装的主智能体类型。
2. 将已识别主智能体以顶层 Agent 形式纳入客户端 Agent 视图。
3. 创建向导第一步只能展示已识别出的主智能体类型。
4. 子智能体可以挂在主智能体之下。
5. 聊天页把主智能体会话按类型分组展示。
6. 客户端在主智能体维度上实现安装、建智能体、发任务、监测与聊天的一体化入口。

## 5. 非目标

1. 本轮不要求服务端同步实现完全一致的主智能体管理逻辑。
2. 本轮不要求新增 Cursor / OpenCode 的深度会话解析能力，只要求先支持安装识别、安装入口接入与类型纳入。
3. 本轮不要求重做整个聊天系统的数据模型。

## 6. 用户角色

### 6.1 本地客户端操作者

关注当前机器上安装了哪些主智能体、如何基于这些主智能体建立子智能体、如何查看这些主智能体的聊天会话。

## 7. 核心场景

### 场景一：客户端启动后自动识别主智能体

当用户本机已安装 Claude、Codex、OpenClaw、Cursor、OpenCode、Hermes 中的任意一种，客户端启动或刷新后应自动识别，并在 Agent 面板中看到对应主智能体。

### 场景二：用户创建子智能体

用户点击新增 Agent 时，向导第一步只能选择已识别出的主智能体类型；若某类主智能体未被识别，则不可选择，并在确定主智能体类型后再进入角色定义等配置步骤。

### 场景三：用户查看聊天会话

聊天页需按主智能体类型分组展示相关会话，例如 Claude、Codex、Hermes、OpenClaw。

### 场景四：用户安装主智能体运行时

用户在客户端设置或引导页中可直接看到主智能体运行时安装状态，并对支持安装的主智能体执行安装动作。

### 场景五：用户向主智能体或其子智能体发任务

用户可以在客户端中把任务指派给主智能体或其子智能体，从而让监测与调度使用同一套 Agent 体系。

## 8. 功能需求

### FR-001 主智能体自动识别

客户端必须支持识别以下主智能体类型的安装状态：

1. `claude`
2. `codex`
3. `openclaw`
4. `cursor`
5. `opencode`
6. `hermes`

### FR-002 主智能体持久化

已识别主智能体必须以稳定的顶层 Agent 记录存在于客户端数据中，具备以下特征：

1. 顶层节点
2. 不依赖手动创建
3. 可作为子智能体父节点
4. 可按框架分组展示

补充约束：

1. `source=local` 的磁盘导入智能体不属于主智能体层。
2. 磁盘导入智能体不得与主智能体混在同一展示分组中。

### FR-003 创建向导受控选择

创建向导第一步必须只显示已识别的主智能体类型；未识别类型不可选择。

### FR-004 主智能体安装入口

客户端必须把主智能体运行时的安装能力统一纳入管控入口：

1. 对已有安装器的主智能体继续支持安装。
2. 安装结果应回流到主智能体识别与状态同步。
3. 安装完成后主智能体应可被创建向导和会话视图消费。

### FR-005 主子智能体关系

用户创建的子智能体必须可以挂靠到对应主智能体之下，并在 Agent 列表中按层级展示。

### FR-006 任务管控一体

主智能体与子智能体必须继续作为客户端任务分配和任务执行的合法目标。

### FR-007 聊天会话按主智能体类型分组

聊天侧边栏必须按主智能体类型展示会话，至少支持：

1. Claude
2. Codex
3. Hermes
4. OpenClaw

若未来 Cursor / OpenCode 具备会话源，也应能复用同样分组机制。

### FR-008 会话分类兼容现有行为

已存在的本地会话继续可打开、继续对话、查看 transcript，不允许因分组改造破坏原有能力。

## 9. 非功能需求

### NFR-001 可扩展

后续新增主智能体类型时，应优先扩展 detector 与分类映射，而非复制粘贴 UI 分支。

### NFR-002 可解释

向导中若无可选主智能体类型，需要明确告诉用户“未检测到可用主智能体”。

### NFR-003 稳定性

主智能体自动识别不能破坏已有手动创建、local sync、gateway sync 行为。

### NFR-004 一体化

客户端内与主智能体相关的安装、创建、任务、聊天与监测入口，必须共享同一套主智能体模型，不允许各自维护不同语义。

## 10. 验收标准

1. 本机安装 Claude/Codex/OpenClaw/Hermes/Cursor/OpenCode 中的任意一项后，客户端可识别其主智能体类型。
2. Agent 面板中存在对应主智能体的顶层卡片。
3. 创建向导第一步仅允许选择已识别主智能体类型。
4. 对支持安装的主智能体可从客户端入口执行安装。
5. 子智能体可以挂到主智能体之下。
6. 主智能体和子智能体继续可作为任务目标。
7. 聊天页会话列表按主智能体类型分组。
8. 现有会话 transcript、继续对话、重命名与颜色设置功能保持可用。
9. `source=local` 的磁盘导入智能体不会再伪装成主智能体。
