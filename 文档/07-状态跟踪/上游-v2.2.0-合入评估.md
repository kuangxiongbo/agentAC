# 上游 Mission Control v2.2.0 合入评估

> 评估日期：2026-07-22
>
> 上游版本：`builderz-labs/mission-control@v2.2.0` (`0552b00`)
>
> 当前定制版本：E-AgentCenter `2.1.59` (`ac71144`)
>
> 结论：禁止整体 merge/cherry-pick；按安全行为和测试用例分批回迁。

## 1. 执行摘要

上游 v2.2.0 相对 v2.1.0 包含 126 个提交、381 个文件变更，新增约 14,068 行、删除约 5,197 行。当前仓库与上游不存在可用 Git 共同祖先，并且上游应用位于仓库根目录，而本项目服务端位于 `mission-control/`，另外还有独立的 `mission-control-client/` 和 `mission-control-tray/`。

因此，本次不能视为常规上游升级。正确方式是：

1. 以当前三端架构和现有业务行为为主线。
2. 只回迁上游已证明有效的安全约束、缺陷修复和测试思想。
3. 对值守、目标监督、Edge 消息、授权和租户模型进行本地化扩展。
4. 每个主题独立 PR、独立迁移、独立回滚，不混入 Tailwind 或页面重构。

文件层面统计：上游 381 个变更文件中有 251 个在本地服务端存在；从本地 `v2.1.37` 到 `2.1.59` 的定制变更与上游只直接重叠 9 个路径，但这不代表低风险，因为数据库、认证、事件、任务和运行时的行为已经跨文件重构。116 个上游非合并提交中，只有 26 个补丁能在路径映射后通过语法级 `git apply --check`，其中多项仍缺少前置依赖，不能直接应用。

## 3. P0：应优先回迁

### P0-1 运行时安装供应链保护

**来源**：上游 #784，后续安全补丁 #869。

**本地风险**：`agent-runtimes.ts` 仍直接执行 OpenClaw/Hermes 的 `curl | bash`，Claude/Codex 使用未固定版本的全局 npm 安装。管理员接口一旦被误用或上游脚本被替换，等同于主机命令执行。

**合入方式**：适配，不直接复制。

- 默认关闭 Dashboard 触发的本地运行时安装。
- 安装脚本先下载到随机私有目录，再校验固定 SHA-256，校验失败必须 fail closed。
- Claude/Codex 固定精确 semver；OpenClaw 固定 reviewed commit 或发行物 digest。
- 保留 Central Mode 禁止本地安装的现有逻辑。
- Edge/托盘升级通道与“安装第三方 Agent Runtime”分开授权，不能共用开关。

**验收**：缺少 hash、hash 错误、版本非精确值、脚本扫描不确定时全部拒绝；合法安装需记录 Workspace/Tenant、操作者和固定版本。

### P0-2 安全加载环境文件

**来源**：上游 #888、#889。

**本地风险**：`docker-entrypoint.sh`、`deploy-standalone.sh` 仍通过 `source`/`.` 执行 `.env`；配置文件中的命令替换、Shell 控制符可被执行。

**合入方式**：基本可复用 `scripts/load-env.sh`，但需补本地兼容测试。

- `.env` 和 `.env.local` 只按 `KEY=VALUE` 数据解析。
- 禁止 `PATH`、`NODE_OPTIONS`、`LD_*`、`DYLD_*` 等进程控制变量。
- 生成的 `.generated-secrets` 同样走安全解析。
- Dockerfile 和 `.dockerignore` 必须明确携带 loader。
- 验证现有中文、URL、JSON、空格、`#`、引号配置兼容性。

### P0-3 WebSocket 稳定重连

**来源**：上游 #832 (`3254772`)。

**本地确认**：服务端 Web UI 和 Edge Web UI 都在 `onclose` 中先把 `handshakeCompleteRef.current` 设为 `false`，随后再判断该值，导致已成功建立的隧道断开后被误判为“初次握手失败”，重连地址可能漂移到 `/gateway-ws` 或 `/gw`。

**合入方式**：小补丁双端同步。

- 清空状态前保存 `wasHandshakeComplete`。
- 只有从未完成握手时才尝试路径 fallback。
- 同时修改 `mission-control` 和 `mission-control-client`。
- 增加“握手成功后瞬断仍使用最后成功 URL”的单元测试。

该补丁直接关系到本地、云端和值守 Agent 的长期在线稳定性，应作为首批独立发布项。

### P0-4 审计与 Agent 身份按 Workspace 隔离

**来源**：上游 #818、#819。

**本地差距**：`audit_log` 仍是实例全局表，部分接口明确依赖该假设；`agents.name` 的初始 schema 仍全局唯一。上游迁移编号 `052` 至 `054` 与本地迁移编号已经冲突，严禁复制编号。

**合入方式**：重新设计本地迁移，建议从 `071` 开始。

- 为 `audit_log` 增加非空 `workspace_id` 和索引，历史数据归入默认 Workspace。
- 所有审计写入必须显式传 Workspace；读取、导出、搜索按 Workspace/Tenant 过滤。
- 重建 agents 表时保留本地新增字段，名称唯一约束改为 `(name, workspace_id)`。
- `session_key`、Edge `client_id` 等外部身份是否全局唯一需单独维持，不能照搬名称约束。
- 值守、目标监督和 Edge 消息审计也要纳入交叉 Workspace 回归测试。

### P0-5 自动任务派发沙箱

**来源**：上游 #766。

**本地必要性**：本项目已经允许值守 Agent 生成目标任务并自动派发，风险高于上游普通人工任务派发。

**合入方式**：只复用约束思想，重写到本地 task/supervision 模型。

- Agent 默认配置支持允许工具、最大预算和工作目录。
- Goal/Plan 可进一步收紧，不能放宽 Agent 默认值。
- 工作目录必须落在 Tenant/Workspace 对应根目录内，并校验 realpath 和软链接。
- 自动生成的监督任务采用更小的默认工具集和预算。
- 本地 `--dangerously-skip-permissions` 是受授权控制的独立机制，不能被上游补丁简单删除；但目标自动派发不得无条件获得该参数。
- 预算同时受单任务上限、目标累计预算和 24 小时值守上限约束。

## 5. P2：作为专项建设，不直接回迁

### 5.1 strict Workspace 隔离

上游 #804 至 #823 的 `shared | strict` 是完整安全主题，但不能直接应用：

- 上游把无 Workspace 归属的本地 session、Gateway、文件系统和 host administration 在 strict 模式下直接拒绝。
- 本项目的 Claude/Codex 会话实际位于 Edge，服务端通过绑定、同步索引和 `session_kind` 建立归属。
- 如果直接使用上游 deny helper，strict Workspace 会阻断人工值守和目标监督；如果继续当成全局资源，又会形成跨租户风险。

本地应先定义统一资源归属键：

```text
tenant_id + workspace_id + client_id + local_agent_id + session_id + session_kind
```

然后按以下顺序实施：

1. 给 Gateway、sync client、session index、Edge message、permission request 建立完整归属。
2. 对 event bus、scheduler、background sync、webhook 增加 Workspace 上下文。
3. 对值守 binding/event/intervention 和 supervision goal/task/event 做跨表一致性检查。
4. 最后再开放 `strict` 开关和 fail-closed 行为。

`brand` 字段只是展示和逻辑分组，目前没有明确业务需求，可不合入。

### 5.2 CI 与发布供应链

上游 #783、#788、#863 至 #865、#877、#880、#885 值得借鉴，但本项目是三包仓库：

- GitHub 实际只识别仓库根目录 `.github/workflows`，不能把上游 workflow 放进 `mission-control/.github` 后认为已生效。
- standalone 边界检查必须允许本项目有意嵌入的 Edge runtime、托盘 DMG、项目文档，同时禁止 `.env`、数据库、PID、日志和私钥。
- Docker 基础镜像应固定 digest，但需兼容国内镜像代理和 `linux/amd64` 生产目标。
- CodeQL、OSV、action SHA pin 应覆盖 server、Edge、tray 三个包。

## 6. 暂不合入或明确放弃

| 上游内容 | 决策 | 原因 |
|---|---|---|
| Tailwind CSS v4 | 暂缓 | 影响 11 主题和三端 UI，安全收益低，容易与当前页面定制混合 |
| 上游 README、宣传图片、Issue 模板 | 不合入产品代码 | 与产品品牌、文档体系和发布流程不一致 |
| 整体替换 task-dispatch | 禁止 | 会覆盖目标监督、9router 路由、Edge 派发和完成验证 |
| 整体替换 migrations | 禁止 | 上游 `052-054` 与本地迁移冲突，且会丢失 Tenant/值守/监督表 |
| 整体替换认证和超级管理员接口 | 禁止 | 本地有用户中心授权、许可证和 Portal Tenant Role |
| 直接启用上游 strict deny | 禁止 | 会错误阻断有远端归属的 Edge 会话和值守链路 |
| Node 24/pnpm 10 升级 | 暂缓 | 当前 Node 22、pnpm 9 与原生依赖及发布镜像已验证，需另立升级项目 |
| Workspace brand | 暂缓 | 暂无已确认业务价值 |

## 7. 建议实施批次

### 批次 A：低耦合高风险修复

1. WebSocket 稳定 URL 重连，server/Edge 双端。
2. `.env` 安全数据解析，覆盖 Docker 与 standalone。
3. 禁用未固定版本的 Runtime 在线安装并增加 hash/version pin。
4. Markdown raw HTML、解析复杂度、CLI URL 校验。

### 批次 B：自主执行安全

1. task-dispatch allowed tools、cwd 和单任务预算。
2. 目标计划只能收紧派发权限。
3. Skill 下载/解压资源上限。
4. 原子配置写入和文件描述符绑定。

### 批次 C：租户和审计闭环

1. `audit_log.workspace_id` 本地迁移。
2. Agent 名称 Workspace 唯一迁移。
3. Event/scheduler/background sync Workspace 上下文。
4. Edge 回执和值守/监督跨表归属校验。

### 批次 D：strict Workspace

1. 建立三端统一资源归属模型。
2. shared/strict 策略和管理入口。
3. 对无归属资源 fail closed。
4. 多租户、双 Edge、双 Workspace 越权 E2E。

### 批次 E：CI 和镜像供应链

1. 三包 CodeQL/OSV/Scorecard。
2. GitHub Action 固定 commit SHA。
3. 定制 standalone/image 边界检查。
4. 固定基础镜像 digest并保留国内代理能力。

## 8. 强制测试门禁

每批至少通过：

- Server 和 Edge `typecheck`、单测、production build。
- 现有人工值守、目标监督、权限申请、Edge 消息回归测试。
- `verify:release-surfaces`。
- 数据库从当前生产 schema 升级、重复启动迁移、备份恢复。
- Central + Edge + Tray 真实环境链路。

专项必须增加：

| 专项 | 必测场景 |
|---|---|
| WebSocket | 成功握手后断线、反向代理路径、休眠恢复、错误凭据不重试 |
| 环境加载 | 命令替换、反引号、控制变量、合法引号/JSON/中文值 |
| Runtime 安装 | 开关关闭、hash 缺失、hash 错误、版本漂移、正确固定版本 |
| 派发沙箱 | `../`、软链接逃逸、工具越权、任务尝试放宽 Goal 权限、预算累计 |
| Workspace | 两 Tenant、同名 Agent、同 session ID、跨 Workspace 查询和事件注入 |
| 值守 | Edge 会话归属、`session_kind`、自动回复、自动停止、重复消息幂等 |
| 监督目标 | 生成任务、纠偏、Worker 完成证明、跨 Workspace task relation 拒绝 |
| 发布 | 镜像不含 DB/.env/日志/私钥，Edge ZIP 和 Tray DMG 哈希仍正确 |

## 9. 最终建议

v2.2.0 值得吸收，但价值主要在安全工程，而不是新业务功能。推荐先完成批次 A，再做批次 B 和 C；strict Workspace 必须建立在本地三端资源归属之上。任何 PR 都不应同时包含 Tailwind v4、页面重构或上游品牌文档。

首个开发 PR 建议只包含 WebSocket #832 的双端修复和回归测试；第二个 PR处理安全 env loader；第三个 PR 单独关闭并固定 Runtime 安装供应链。这样能最快降低真实生产风险，也最容易回滚和验证。
