# 联调步骤-人工值守（Phase 1 E2E）

## 1. 环境前提

| 角色 | 地址 | 说明 |
|------|------|------|
| **中心服** | `http://127.0.0.1:5000` 或生产 `https://agent.1sheng.work` | `MC_ENABLE_LOCAL_MONITORING=false`（centralMode） |
| **边缘客户端** | `http://127.0.0.1:5001` | `mission-control-client`，`pnpm dev` |
| **Bridge** | 中心 **5002** | 客户端 `.env.local` 配置 `MC_REMOTE_SERVER_URL=ws://127.0.0.1:5002`（或生产 wss） |

检查清单：

- [ ] 中心服 `pnpm dev` 已启动，侧栏可见 **「人工值守」**（仅 centralMode）
- [ ] 客户端已启动，Bridge 显示 **已连接**（`GET /api/bridge/clients` 或 UI 节点列表）
- [ ] Worker 为 **Claude/Codex** 本地运行时，且已有 **专用 `session_key`**（绑定必需）

开发环境可二选一开通功能：

1. **UI**：管理员登录 → `PATCH /api/human-watch/policy`（见下）
2. **环境变量**：中心服启动前设置 `MC_HUMAN_WATCH_ENABLED=true`（跳过租户表开关，仅联调用）

## 2. 步骤一：开通租户

**需要 admin 角色**（或本地免登时确保当前用户为 admin）。

```bash
export MC_BASE="http://127.0.0.1:5000"
# 从浏览器 DevTools → Application → Cookie 复制 mc_session=...
export MC_COOKIE="mc_session=你的会话值"

curl -sS "$MC_BASE/api/human-watch/policy" -H "Cookie: $MC_COOKIE" | jq .

curl -sS -X PATCH "$MC_BASE/api/human-watch/policy" \
  -H "Cookie: $MC_COOKIE" \
  -H "Content-Type: application/json" \
  -d '{"enabled":true}' | jq .
# 预期：{ "enabled": true }
```

---

## 3. 步骤二：创建值守 Agent（边缘）

### 方式 A：UI（推荐）

1. 中心服侧栏 → **人工值守**
2. **客户端节点** 下拉选在线 Bridge 节点（如 `mac-xxx`）
3. 填写名称、选择 **Claude** 或 **Codex** → **创建值守**
4. 舰队页对应分组出现 Agent，带 **「值守」** 徽标

### 方式 B：API

```bash
curl -sS -X POST "$MC_BASE/api/human-watch/stewards" \
  -H "Cookie: $MC_COOKIE" \
  -H "Content-Type: application/json" \
  -d '{
    "client_id": "你的clientId",
    "name": "值守-测试",
    "framework": "claude-code"
  }' | jq .
# 预期 201；边缘自动 provision-session
```

确认边缘已同步到中心索引：

```bash
curl -sS "$MC_BASE/api/agents?include_bridge=1" -H "Cookie: $MC_COOKIE" | jq '.agents[] | select(.role=="human-watch")'
```

## 4. 步骤三：绑定 Worker

### 前提

- Worker 与值守 **同一 `client_id`**
- **framework 一致**（如 Worker 为 Claude 会话 → 值守选 `claude-code`）
- Worker 在边缘已有 **`session_key`**（专用会话已 provision）

### UI

1. 人工值守面板 → **监视绑定**
2. 选同一节点 → Worker 下拉 → 值守下拉 → **保存绑定**

### API

```bash
curl -sS -X POST "$MC_BASE/api/human-watch/bindings" \
  -H "Cookie: $MC_COOKIE" \
  -H "Content-Type: application/json" \
  -d '{
    "client_id": "你的clientId",
    "worker_local_agent_id": 10,
    "steward_local_agent_id": 9,
    "mode": "auto_send"
  }' | jq .
# 预期 201；响应 binding.worker_session_id 应有值
```

列出绑定：

```bash
curl -sS "$MC_BASE/api/human-watch/bindings" -H "Cookie: $MC_COOKIE" | jq .
```

## 5. 步骤四：触发编排

### 方式 A：自然触发（推荐验证真实链路）

1. 在边缘打开 Worker 的 CLI 会话
2. 让 assistant 输出 **确认类话术**（如「请确认选择 A 还是 B」），并 **停止操作 ≥90s**（满足 L1 空闲 + L3 确认文案）
3. 中心编排订阅 `session.transcript.updated`（边缘 Bridge 推送）后自动评估

### 方式 B：手动触发（联调最快）

```bash
BINDING_ID=1   # 上一步返回的 binding.id

curl -sS -X POST "$MC_BASE/api/human-watch/evaluate" \
  -H "Cookie: $MC_COOKIE" \
  -H "Content-Type: application/json" \
  -d "{\"binding_id\":$BINDING_ID}" | jq .
```

**注意**：手动触发仍会拉真实 transcript；若规则未命中，只会写 `rule_evaluated`（decision=noop），不会代发。

加速命中可在 binding 的 `rules_override` 中临时调低阈值，例如：

```json
{
  "idle_timeout_seconds": 30,
  "grace_after_prompt_seconds": 0,
  "confirmation_patterns": ["请确认", "which option"]
}
```

通过 `PATCH /api/human-watch/bindings/{id}` 写入。

## 6. 步骤五：验收留痕

### 6.1 API 查询

```bash
curl -sS "$MC_BASE/api/human-watch/interventions?client_id=你的clientId&limit=20" \
  -H "Cookie: $MC_COOKIE" | jq .
```

**代发成功**（HW-TC-A01）预期事件链：

1. `rule_evaluated`（decision=`auto_send`）
2. `intervention_attempt`
3. `intervention_completed`（`outcome=success`）

**指纹去重**（HW-TC-A03）：再次 `POST .../evaluate`，应出现 `intervention_skipped`，`skip_reason=fingerprint_duplicate`，且 **无第二次** continue。

**Bridge 离线**（HW-TC-A04）：断开客户端 Bridge 后 evaluate → `skip_reason=bridge_offline`。

### 6.2 UI

- Worker 或值守 **智能体详情** → **干预记录** Tab：最近 20 条倒序
- 聊天会话列表：**不应**出现值守判官专用会话（已按 `session_key` 过滤）

### 6.3 SQLite（中心库）

```bash
sqlite3 mission-control/.data/mission-control.db "
  SELECT id, event_type, decision, outcome, skip_reason, substr(prompt_preview,1,40), created_at
  FROM human_watch_interventions
  ORDER BY id DESC LIMIT 15;
"
```

### 6.4 导出 CSV（admin）

浏览器或 curl（需 admin）：

`GET /api/export?type=human_watch_interventions&format=csv`

### 6.5 边缘 Worker 会话

代发成功后，Worker 会话 transcript 应出现 **新的 user 消息**（与聊天页手动发送等价），来源为 Bridge `session_continue`。

## 7. 常见问题

| 现象 | 排查 |
|------|------|
| 侧栏无「人工值守」 | 确认 centralMode；刷新 capabilities |
| 创建值守 503 | Bridge 离线；检查 `MC_REMOTE_SERVER_URL` |
| 绑定 400 framework | Worker 与值守 runtime 不一致 |
| 只有 rule_evaluated noop | transcript 未满足 L1∧(L2∨L3)；调 rules_override 或改 Worker 对话 |
| 有 attempt 无 success | 看 `intervention_completed.outcome=failed` 的 `error_message` |
| 编排不自动跑 | 中心 scheduler 是否启动；`worker_session_id` 是否与事件 sessionId 一致 |

## 9. Phase 2（L4 判官 + 扫漏）

### 9.1 启用 L4 判官（HW-018）

在边缘值守 Agent 的 `config.steward` 中设置（可通过 PATCH agent 或创建时写入）：

```json
{
  "steward": {
    "llm_enabled": true,
    "judge_prompt_template": "根据以下 Worker 摘要，只输出要发给 Worker 的一句续作指令：\n{summary}"
  }
}
```

规则命中且 `mode=auto_send` 时，中心会经 Bridge 调用 `steward_judge_request`，在值守专用 `session_key` 上跑 CLI，将 `reply` 作为 Worker `session_continue` 的 prompt。

### 9.2 启用 30 分钟扫漏（HW-019）

```json
{
  "steward": {
    "llm_sweep_enabled": true,
    "llm_sweep_interval_minutes": 30
  }
}
```

编排器每 60s 检查绑定；到期则执行一次规则评估并写入 `event_type=llm_sweep`（`llm_sweep=1`）。可在干预记录 Tab 或 `GET /api/human-watch/interventions` 筛选查看。
