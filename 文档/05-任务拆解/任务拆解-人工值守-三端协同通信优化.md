# 任务拆解-人工值守-三端协同通信优化

## 1. 执行原则

- 先做可靠消息内核，再接人工值守。
- Bridge push 只做唤醒，pull/lease/ack 才是事实。
- 本地执行前必须落 local inbox，执行结果必须落 local outbox。
- 不破坏旧 Bridge RPC；新链路按 capability 灰度。
- 所有人工值守消息必须能通过 `correlation_id/message_id` 追踪到 audit。

## 4. Phase 1 DoD

1. 云端能创建、查询、lease、ack、fail 消息。
2. 本地能 pull 消息、落 inbox、执行、写 outbox、ack 云端。
3. 人工值守 assist 在客户端离线时返回 `queued=true`。
4. 客户端上线后 queued assist 自动执行并写回 Worker。
5. 同一 Worker session 并发 continue 按顺序执行。
6. 重复 `idempotency_key` 不重复创建和执行。
7. 中心 UI/API 能看到 pending/leased/failed/dead letter。
8. 新链路有灰度开关，关闭后回到 2.1.18 实时 RPC 行为。

## 5. 测试计划

| 测试 | 目标 |
|------|------|
| 云端消息状态机单测 | 覆盖 pending/leased/completed/failed/dead_letter/cancelled |
| 幂等单测 | 相同幂等键只创建一条消息 |
| Lease 超时单测 | 超时消息重新 pending |
| 本地 mailbox 单测 | 重启后恢复 inbox/outbox |
| 人工值守离线集成 | Bridge 离线时 assist queued，上线后执行 |
| 串行集成 | 同 session 多条 continue 不乱序 |
| 高危审批回归 | 新消息机制不绕过权限请求风控 |

## 6. 发布与回滚

发布：

1. 先发布云端表/API，默认不开启。
2. 发布本地 runtime 和托盘状态展示。
3. 对内部租户开启 `MC_RELIABLE_EDGE_MESSAGES=1`。
4. 灰度人工值守 assist queued delivery。

回滚：

1. 关闭 `MC_RELIABLE_EDGE_MESSAGES`。
2. `/api/human-watch/assist` 回到实时 Bridge RPC。
3. 保留消息表，不删除数据。
4. dead letter 和 pending 消息不自动执行，等待后续恢复。
