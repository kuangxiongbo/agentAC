# 框架设计-客户端主智能体识别与聊天聚类

## 1. 设计目标

在客户端内部建立“主智能体层”和“子智能体层”的清晰结构，并让安装、建智能体、发任务、会话列表都围绕主智能体类型统一工作。

## 2. 总体设计

### 2.1 主智能体层

主智能体由本机运行时检测自动产生，代表本机可用的智能体平台入口，例如 Claude、Codex、OpenClaw、Cursor、OpenCode、Hermes。

### 2.2 子智能体层

子智能体由用户通过创建向导新增，必须挂在主智能体之下或作为主智能体类型下的逻辑扩展 Agent。

### 2.3 会话层

会话数据仍然来源于现有 sessions API，但在 UI 侧要新增“主智能体类型”分类维度。

### 2.4 管控层

安装入口、创建向导、任务分配都要围绕主智能体层运转，形成统一的控制入口。

## 3. 模块边界

### 3.1 Detector 模块

负责检测本机运行时是否存在。

### 3.2 Runtime Agent Sync 模块

负责将检测结果映射为顶层主智能体 Agent 记录。

### 3.3 Runtime Install 模块

负责统一暴露主智能体运行时安装能力，并让安装结果回流到 detection 与 agent sync。

### 3.4 Create Agent Modal

负责读取可用主智能体类型并限制用户选择。

### 3.5 Conversation List

负责把 sessions API 返回的会话按主智能体类型分组渲染。

### 3.6 Task Dispatch / Assignment

继续复用现有任务体系，但主智能体和子智能体都要成为统一的任务目标。

## 4. 关键数据流

1. 客户端启动或调度执行 runtime detection。
2. detection 输出“已安装主智能体类型列表”。
3. runtime agent sync 将其落成顶层 Agent 记录。
4. Agent 面板按 framework 分组显示这些主智能体。
5. 创建向导读取已识别主智能体类型，只允许这些类型被选择。
6. 聊天侧边栏把 sessions 映射到主智能体类型后分组显示。
7. 任务面板与任务路由继续使用同一套 Agent 记录进行指派。

## 5. 分组映射策略

建议主智能体类型到会话类型映射如下：

1. `claude` -> `claude-code`
2. `codex` -> `codex-cli`
3. `hermes` -> `hermes`
4. `openclaw` -> `gateway`
5. `cursor` -> 未来扩展
6. `opencode` -> 未来扩展

## 6. 扩展策略

1. Runtime detector 列表新增框架时，同步更新主智能体同步逻辑。
2. 会话分组使用统一映射表，不写散乱条件判断。
3. UI 使用统一“主智能体类型元数据”渲染标题、图标和空状态。
