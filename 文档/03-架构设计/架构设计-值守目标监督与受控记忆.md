# 架构设计-值守目标监督与受控记忆

## 1. 架构目标

在现有人工值守、任务中心和三端可靠通信之上增加目标监督控制面。值守 Agent 负责认知判断，中心服务负责状态机、校验、授权和落库，Edge 负责运行 CLI，Worker 负责执行。

设计原则：

1. 模型不直接修改业务状态，只返回结构化建议。
2. Goal、Task、Message、Session 各自只有一个事实源。
3. 事件驱动为主，周期扫描只作补偿。
4. 执行判断与最终验收分离。
5. 记忆先候选后晋升，不做不可审计的自我改写。
6. 同一 Goal 同时只有一个监督 lease。

## 2. 总体架构

```text
用户/Web
  -> Goal API
  -> Goal Supervisor Orchestrator
       -> Steward Goal Session: 计划/监督建议/验收建议
       -> Policy & Budget Guard
       -> Task Service / Task Queue
       -> Reliable Edge Messages / Bridge
            -> Worker Sessions
       -> Evidence Collector
       -> Automatic Memory Pipeline
  -> Goal / Plan / Task Relation / Supervision Event / Memory DB
```

同一值守 Agent 使用两个隔离会话：

- Reactive Watch Session：处理 Worker 当前等待确认，输入窗口短、强调快速响应。
- Goal Supervisor Session：持有目标、计划和阶段性摘要，负责跨任务长期监督。

两个会话可以共享已批准记忆，但不得共享未经整理的完整 transcript。

## 3. 模块设计

### 3.1 Goal Service

职责：

- 创建、读取、暂停、恢复、取消 Goal。
- 执行合法状态迁移和乐观并发控制。
- 管理预算、截止时间和用户确认。
- 产生 append-only supervision event。

### 3.2 Planner

中心构造目标上下文，通过 Bridge/可靠消息调用值守 Goal Session。模型返回 `GoalPlanDraft`，中心执行：

1. JSON schema 校验。
2. 任务数量和文本长度限制。
3. DAG 无环校验。
4. 风险与预算检查。
5. Worker 能力要求规范化。
6. 保存不可变 Plan Version。

Planner 不直接创建任务；只有计划获批后由 Dispatcher 创建。

### 3.3 Worker Matcher

输入：任务能力需求、允许节点、Worker 列表、在线状态、负载和历史结果。

硬过滤：

- 排除 `agent_kind=human_watch`。
- 排除无可用 session、框架不支持、节点不允许或离线超时 Worker。
- 排除用户黑名单和高风险不授权 Worker。

评分因素：能力匹配、当前负载、近期成功率、同项目经验、数据本地性。评分和选择理由写入 supervision event。

### 3.4 Dispatcher

复用 `tasks` 表和 task queue：

- 创建任务时写 `metadata.goal_id`、计划版本、验收标准和幂等键。
- 建立 `supervision_goal_tasks` 关系。
- 依赖未满足的任务保持 blocked/inbox，不进入 Worker 队列。
- Worker 领取后由既有任务状态机执行。

### 3.5 Supervisor Loop

事件来源：

- task created/claimed/updated/completed/failed。
- Worker transcript、permission request、human-watch event。
- Edge message ack/fail、Bridge connect/disconnect。
- deadline/budget/watchdog timer。

处理流程：

```text
event -> acquire goal lease -> rebuild bounded snapshot
      -> deterministic checks
      -> optional steward evaluate
      -> policy validation
      -> execute one idempotent action
      -> append event -> release lease
```

每轮最多执行一个主要动作，避免一次模型回复产生大量不可控变更。

### 3.6 Correction Executor

纠偏动作分三类：

- 会话动作：继续、询问进度、明确纠偏，通过 reliable `session.continue.requested`。
- 任务动作：重试、换 Worker、补任务，通过 Task Service。
- 目标动作：重规划、暂停、转人工、失败，通过 Goal Service。

所有动作必须包含 `idempotency_key=goal:{goalId}:event:{sourceEvent}:action:{kind}`。

### 3.7 Evidence Collector 与 Verifier

Evidence Collector 从任务 outcome、文件/API 检查、测试、消息结果和人工确认中收集证据引用，不复制大文件正文。

Verifier 使用独立 prompt 和会话目的，对每条 success criterion 输出：

- `pass` / `fail` / `unknown`
- `evidence_refs[]`
- `reason`
- `followup_task`（可选）

Verifier 不能仅以任务状态 done 作为通过依据。

### 3.8 Memory Pipeline

```text
Goal/Intervention outcome
  -> Memory Extractor
  -> deterministic redaction/dedup/conflict check
  -> approved memory (active immediately)
  -> retrieval + usage event
  -> outcome score
  -> confidence update / disable / restore / supersede / expire
```

记忆作用域：user、project、workspace、tenant、steward。默认最小作用域，不跨租户。

## 4. 数据模型

### 4.1 `supervision_goals`

关键字段：

- `id TEXT PRIMARY KEY`
- `workspace_id`、`tenant_id`
- `steward_agent_id`、`steward_session_id`
- `title`、`objective`
- `success_criteria_json`、`constraints_json`
- `allowed_workers_json`
- `status`、`priority`
- `budget_json`、`usage_json`
- `current_plan_version`
- `requires_plan_approval`
- `deadline_at`
- `created_by`、`created_at`、`updated_at`、`completed_at`
- `version INTEGER` 用于乐观锁

### 4.2 `supervision_goal_plans`

- `id TEXT PRIMARY KEY`
- `goal_id`
- `version`
- `status=draft|approved|superseded|rejected`
- `plan_json`
- `rationale`
- `source_event_id`
- `created_by_type=user|steward|system`
- 唯一键 `(goal_id, version)`

### 4.3 `supervision_goal_tasks`

- `goal_id`、`task_id`
- `plan_version`
- `logical_task_key`
- `dependencies_json`
- `acceptance_criteria_json`
- `assigned_agent_id`、`assigned_session_id`
- `retry_count`、`reassignment_count`
- 唯一键 `(goal_id, logical_task_key, plan_version)`

### 4.4 `supervision_events`

append-only：

- `id INTEGER PRIMARY KEY AUTOINCREMENT`
- `goal_id`、`task_id`
- `event_type`
- `actor_type`、`actor_id`
- `decision`、`reason`
- `evidence_json`、`action_json`
- `message_id`、`correlation_id`、`idempotency_key`
- `created_at`

### 4.5 `supervision_leases`

- `goal_id PRIMARY KEY`
- `owner_id`
- `lease_expires_at`
- `updated_at`

通过事务领取，超时可恢复。

### 4.6 `steward_memories`

- `id TEXT PRIMARY KEY`
- `workspace_id`、`tenant_id`
- `scope_type`、`scope_id`
- `category=preference|fact|episode|procedure`
- `content`、`summary`
- `source_refs_json`、`evidence_json`
- `confidence REAL`
- `status=candidate|approved|rejected|superseded|expired`
- `supersedes_id`
- `effective_at`、`expires_at`
- `created_by_type`、`reviewed_by`
- `created_at`、`updated_at`

兼容状态语义：`approved` 表示当前生效，`rejected` 表示人工停用；`candidate` 仅用于展示升级前遗留数据。人工停用具有粘性，重复提炼只补充证据，不自动恢复为生效状态。

### 4.7 `steward_memory_usage`

记录 memory 在某次 goal/judge 中是否被检索、是否采纳、最终 outcome 和 score，为降权/晋升提供事实。

## 5. 状态与一致性

### 5.1 Goal 状态机

状态转换由 Goal Service 白名单控制。每次转换使用 `WHERE id=? AND version=?` 乐观锁，成功后 version + 1。

### 5.2 计划版本

计划不可更新，只能新增版本。重规划后旧版本标为 superseded，但历史任务和事件仍可追踪。

### 5.3 任务幂等

任务创建使用 `(goal_id, logical_task_key, plan_version)` 唯一键；重复事件不会创建第二个任务。

### 5.4 会话串行

同一 Worker session 的 continue 继续使用 Edge message `serial_key`。Goal supervisor 不直接绕过 Mailbox。

## 6. 安全模型

1. Goal 创建和计划批准需要 operator 权限。
2. 值守 Agent 只能操作绑定/允许范围内 Worker。
3. 高风险动作创建 permission request，不能直接执行。
4. Memory 内容写入前做 secret/credential/PII 检测；命中则拒绝或脱敏。
5. 记忆检索强制 workspace/tenant/scope 过滤。
6. 用户可以查看、拒绝、纠正和删除可删除的记忆；审计事件保留最小必要事实。

## 7. 资源与循环控制

每个 Goal 保存并强制执行：

- `max_tasks`
- `max_parallel_workers`
- `max_retries_per_task`
- `max_replans`
- `max_runtime_seconds`
- `max_model_calls`
- `max_estimated_cost`

Supervisor 每次动作后重新计算 usage；任何限制达到即暂停并转人工。

## 8. 可观测性

指标：

- goal 各状态数量和停留时间。
- plan 生成/修正次数。
- task 分派、重试、换人和完成率。
- correction 成功率。
- verifier pass/fail/unknown。
- memory candidate/approved/used/effective。
- Edge message 完成率和 P50/P95。
- Bridge 重连、Mailbox backlog、runtime process_id 和重复监听数。

所有日志带 `goal_id`、`correlation_id`，敏感文本只保留 hash/预览。

## 9. 容错

- 中心重启：lease 超时后继续监督，Goal/Plan/Event 不丢失。
- Edge 离线：消息 pending，Goal 标记 blocked_edge_offline，不重复分派。
- Worker 会话丢失：尝试同步/重新 provision；失败转人工或换 Worker。
- Steward judge 失败：退避重试；达到上限进入 blocked，不使用固定“继续”冒充判断。
- 验收超时：暂停并显示缺失证据。

## 10. 分阶段实现

1. P0：schema、Goal CRUD、状态机、审计。
2. P1：结构化计划、任务创建、单 Worker 监督。
3. P2：多 Worker、依赖、纠偏、重规划和验收。
4. P3：记忆候选、审核、检索和效果反馈。
5. P4：UI、72 小时灰度、生产发布。
