## 2. 干预留痕（关键）

### HW-TC-A01 代发成功留痕

- **前置**：租户已开通；binding 启用；Bridge 在线；规则可命中。
- **步骤**：触发编排代发 → continue 成功。
- **预期**：`human_watch_interventions` 含 `intervention_attempt` + `intervention_completed`（`outcome=success`）；`prompt_preview` 非空；`fingerprint` 一致。

### HW-TC-A02 代发失败留痕

- **前置**：模拟 Bridge continue 返回错误。
- **预期**：`intervention_completed` 且 `outcome=failed`；`error_message` 有值；**无** success 记录。

### HW-TC-A03 指纹去重跳过留痕

- **前置**：同 fingerprint 已成功代发过一次。
- **预期**：`intervention_skipped`，`reason=fingerprint_duplicate`；不发起第二次 continue。

### HW-TC-A04 Bridge 离线跳过留痕

- **前置**：client 离线。
- **预期**：`intervention_skipped`，`reason=bridge_offline`；无 `intervention_completed` success。

### HW-TC-A05 查询 API 租户隔离

- **步骤**：租户 A 写入；租户 B 调用 `GET /api/human-watch/interventions`。
- **预期**：B 看不到 A 记录。

### HW-TC-A06 Worker 详情 UI

- **步骤**：打开 Worker 详情「干预记录」。
- **预期**：最近 20 条倒序；含时间、结果、规则摘要。

## 4. 权限请求与选项决策（V1.4）

### HW-TC-P01 创建权限请求

- **前置**：用户具备 operator 权限。
- **步骤**：调用 `POST /api/permission-requests`，传入 `request_type`、`title`、`prompt`、`risk`、两个以上 `options`。
- **预期**：返回 201；DB 中 `permission_requests.status=pending`；广播 `permission.requested`。

### HW-TC-P02 值守 Agent 按选项批准低/中风险

- **前置**：存在 `risk=medium` 的 pending 请求。
- **步骤**：调用 `POST /api/permission-requests/{id}/decision`，`deciderType=steward_agent`，`optionId` 指向 `action=approve` 的选项。
- **预期**：请求状态变为 `approved`；写入 `permission_request_decisions`；广播 `permission.decided`。

### HW-TC-P03 非法选项拒绝

- **步骤**：对 pending 请求提交不存在的 `optionId`。
- **预期**：400；请求仍为 `pending`；不写决策记录。

### HW-TC-P04 重复决策拒绝

- **步骤**：同一请求先批准，再提交第二次决策。
- **预期**：409/400；状态保持第一次结果；只保留一次有效决策。

### HW-TC-P05 过期请求不可决策

- **前置**：`expires_at` 小于当前时间。
- **步骤**：提交决策。
- **预期**：请求状态变为 `expired`；返回错误；不批准。

### HW-TC-P06 值守 Agent 不可批准高危请求

- **前置**：存在 `risk=high` 或 `critical` 的 pending 请求。
- **步骤**：`deciderType=steward_agent` 选择 `action=approve`。
- **预期**：403；请求仍 pending；可选择拒绝或转人工。

### HW-TC-P07 普通回复不改变权限状态

- **步骤**：值守 Agent 只通过聊天回复“同意”。
- **预期**：`permission_requests.status` 不变化；Worker 不应恢复执行，除非调用专门决策 API/MCP。

### HW-TC-P08 看门狗不误判等待审批的任务（2.1.17）

- **前置**：任务 `in_progress` 超过 10 分钟，对应 agent 存在 `permission_requests.status='pending'`。
- **步骤**：运行 `requeueStaleTasks()`。
- **预期**：任务状态保持 `in_progress`，不进入 `assigned`/`failed`；返回消息包含 "awaiting human approval" 计数。对照用例：agent 离线且无 pending 审批时仍正常 requeue。
- **自动化**：`mission-control/src/lib/__tests__/task-dispatch-stale.test.ts`

### HW-TC-P09 风险判断统一由值守侧规则裁定（2.1.17）

- **步骤**：创建 `permission_request`，worker 传入与实际内容不符的 `risk` 值。
- **预期**：`human_watch_events.priority` 由 `isDangerousPermissionRequest()` 规则结果决定，不直接采用 worker 自报的 `risk`。
- **自动化**：`mission-control/src/lib/__tests__/permission-requests.test.ts`

### HW-TC-P10 judge 建议采纳/驳回审计（2.1.17）

- **步骤**：人工 resolve 一个事件，分别测试 resolved_action 与 judge 原始 suggested_action 相同/不同两种情况；另测 system 自动 resolve 不应记录该审计。
- **预期**：`context.event_audit` 出现 `judge_suggestion_outcome`，`accepted` 字段正确反映是否一致；system 来源不产生该记录。
- **自动化**：`mission-control/src/lib/__tests__/human-watch-judge-feedback.test.ts`

### HW-TC-P11 高优先级事件接入 webhook（2.1.17）

- **步骤**：账号配置 webhook 订阅 `human_watch.event.high`；触发 `priority=high` 和 `priority=medium` 两种 `human_watch.event`。
- **预期**：`high` 触发额外的 `human_watch.event.high` 投递；`medium` 不触发该订阅的 webhook。
- **自动化**：`mission-control/src/lib/__tests__/webhooks-human-watch.test.ts`
