## 2. 干预留痕（关键）

### HW-TC-A01 代发成功留痕

- **前置**：租户已开通；binding 启用；Bridge 在线；规则可命中。
- **步骤**：触发编排代发 → continue 成功。
- **预期**：`human_watch_interventions` 含 `intervention_attempt` + `intervention_completed`（`outcome=success`）；`prompt_preview` 非空；`fingerprint` 一致。

### HW-TC-A02 代发失败留痕

- **前置**：模拟 Bridge continue 返回错误。
- **预期**：`intervention_completed` 且 `outcome=failed`；`error_message` 有值；**无** success 记录。

### HW-TC-A03 指纹去重跳过留痕

- **前置**：同 fingerprint 已成功代发过一次。
- **预期**：`intervention_skipped`，`reason=fingerprint_duplicate`；不发起第二次 continue。

### HW-TC-A04 Bridge 离线跳过留痕

- **前置**：client 离线。
- **预期**：`intervention_skipped`，`reason=bridge_offline`；无 `intervention_completed` success。

### HW-TC-A05 查询 API 租户隔离

- **步骤**：租户 A 写入；租户 B 调用 `GET /api/human-watch/interventions`。
- **预期**：B 看不到 A 记录。

### HW-TC-A06 Worker 详情 UI

- **步骤**：打开 Worker 详情「干预记录」。
- **预期**：最近 20 条倒序；含时间、结果、规则摘要。

### HW-TC-A07 连续确认值守容量

- **前置**：binding 为 `auto_send`；租户规则使用默认 `max_interventions_per_hour=60` 且 `max_interventions_window_seconds=86400`；Worker 连续提出多轮等待确认问题。
- **步骤**：连续触发 7 次以上不同 fingerprint 的等待确认。
- **预期**：第 7 次及后续不同问题仍可由值守 Agent 判官生成回复并通过 MCP/Bridge 发送；24 小时内超过默认上限才触发 `rate_limited`。

## 4. 权限请求与选项决策（V1.4）

### HW-TC-P01 创建权限请求

- **前置**：用户具备 operator 权限。
- **步骤**：调用 `POST /api/permission-requests`，传入 `request_type`、`title`、`prompt`、`risk`、两个以上 `options`。
- **预期**：返回 201；DB 中 `permission_requests.status=pending`；广播 `permission.requested`。

### HW-TC-P02 值守 Agent 按选项批准低/中风险

- **前置**：存在 `risk=medium` 的 pending 请求。
- **步骤**：调用 `POST /api/permission-requests/{id}/decision`，`deciderType=steward_agent`，`optionId` 指向 `action=approve` 的选项。
- **预期**：请求状态变为 `approved`；写入 `permission_request_decisions`；广播 `permission.decided`。

### HW-TC-P03 非法选项拒绝

- **步骤**：对 pending 请求提交不存在的 `optionId`。
- **预期**：400；请求仍为 `pending`；不写决策记录。

### HW-TC-P04 重复决策拒绝

- **步骤**：同一请求先批准，再提交第二次决策。
- **预期**：409/400；状态保持第一次结果；只保留一次有效决策。

### HW-TC-P05 过期请求不可决策

- **前置**：`expires_at` 小于当前时间。
- **步骤**：提交决策。
- **预期**：请求状态变为 `expired`；返回错误；不批准。

### HW-TC-P06 值守 Agent 不可批准高危请求

- **前置**：存在 `risk=high` 或 `critical` 的 pending 请求。
- **步骤**：`deciderType=steward_agent` 选择 `action=approve`。
- **预期**：403；请求仍 pending；可选择拒绝或转人工。

### HW-TC-P07 普通回复不改变权限状态

- **步骤**：值守 Agent 只通过聊天回复“同意”。
- **预期**：`permission_requests.status` 不变化；Worker 不应恢复执行，除非调用专门决策 API/MCP。

### HW-TC-P08 看门狗不误判等待审批的任务（2.1.17）

- **前置**：任务 `in_progress` 超过 10 分钟，对应 agent 存在 `permission_requests.status='pending'`。
- **步骤**：运行 `requeueStaleTasks()`。
- **预期**：任务状态保持 `in_progress`，不进入 `assigned`/`failed`；返回消息包含 "awaiting human approval" 计数。对照用例：agent 离线且无 pending 审批时仍正常 requeue。
- **自动化**：`mission-control/src/lib/__tests__/task-dispatch-stale.test.ts`

### HW-TC-P09 风险判断统一由值守侧规则裁定（2.1.17）

- **步骤**：创建 `permission_request`，worker 传入与实际内容不符的 `risk` 值。
- **预期**：`human_watch_events.priority` 由 `isDangerousPermissionRequest()` 规则结果决定，不直接采用 worker 自报的 `risk`。
- **自动化**：`mission-control/src/lib/__tests__/permission-requests.test.ts`

### HW-TC-P10 judge 建议采纳/驳回审计（2.1.17）

- **步骤**：人工 resolve 一个事件，分别测试 resolved_action 与 judge 原始 suggested_action 相同/不同两种情况；另测 system 自动 resolve 不应记录该审计。
- **预期**：`context.event_audit` 出现 `judge_suggestion_outcome`，`accepted` 字段正确反映是否一致；system 来源不产生该记录。
- **自动化**：`mission-control/src/lib/__tests__/human-watch-judge-feedback.test.ts`

### HW-TC-P11 高优先级事件接入 webhook（2.1.17）

- **步骤**：账号配置 webhook 订阅 `human_watch.event.high`；触发 `priority=high` 和 `priority=medium` 两种 `human_watch.event`。
- **预期**：`high` 触发额外的 `human_watch.event.high` 投递；`medium` 不触发该订阅的 webhook。
- **自动化**：`mission-control/src/lib/__tests__/webhooks-human-watch.test.ts`

### HW-TC-P12 Worker 主动求助触发值守回复（2.1.18）

- **前置**：Worker 与值守 Agent 已绑定，Bridge 在线，binding 为 `auto_send`。
- **步骤**：Worker 调用 `mc_create_watch_event`，只传 `prompt`，不传 `options`。
- **预期**：平台调用 `/api/human-watch/assist`；创建 `human_watch_events(source=worker_tool)`；调用值守 judge；通过 `session_continue` 把值守回复写回 Worker 会话；写入 `intervention_attempt` 与 `intervention_completed`。
- **自动化**：`mission-control/src/lib/__tests__/human-watch-orchestrator.test.ts`、`mission-control/src/lib/__tests__/codex-mcp-injection.test.ts`

### HW-TC-P13 Worker 等待用户回复话术命中规则（2.1.18）

- **步骤**：Worker 最后一条 assistant 消息包含“你希望/哪个/还是/是否/?”等等待用户回复语义，且超过空闲阈值。
- **预期**：`evaluateHumanWatchRules()` 命中 `awaiting_user_response` 与 `idle_timeout`。
- **自动化**：`mission-control/src/lib/__tests__/human-watch-rules.test.ts`

### HW-TC-P14 人工值守可靠 mailbox 离线排队与恢复（2.1.19）

- **前置**：开启 `MC_RELIABLE_EDGE_MESSAGES=1`，Worker 与值守 Agent 已绑定，Edge 支持 `reliable_mailbox` capability。
- **步骤**：Edge 离线时调用 `/api/human-watch/assist?delivery_mode=auto` 或 `queue_if_offline=true`；随后恢复 Edge，并触发 `/api/local/mailbox/drain`。
- **预期**：云端返回 `queued=true` 与 `message_id/correlation_id`；消息进入 `edge_messages(pending)`；本地上线后 lease 消息、调用值守 judge、继续写回 Worker session，并 ack 云端。
- **自动化**：`mission-control/src/lib/__tests__/human-watch-assist-route.test.ts`、`mission-control-client/src/lib/__tests__/local-mailbox-human-watch-assist.test.ts`

### HW-TC-P15 历史值守 Agent 自动创建 judge session（2.1.20）

- **前置**：Worker 与值守 Agent 已绑定，值守 Agent 是历史数据且 `session_key` 为空。
- **步骤**：云端投递 `human_watch.assist.requested`，本地 Mailbox drain 后执行值守 judge。
- **预期**：本地 runtime 自动 provision dedicated judge session，取得值守回复，随后把回复继续写入 Worker session；不再返回 `Steward has no dedicated judge session yet`。
- **自动化**：`mission-control-client/src/lib/__tests__/human-watch-judge.test.ts`、`mission-control-client/src/lib/__tests__/local-mailbox-human-watch-assist.test.ts`

### HW-TC-P16 Edge runtime native ABI 校验（2.1.20）

- **步骤**：执行 Edge runtime 打包脚本。
- **预期**：打包前 `pnpm rebuild better-sqlite3` 成功；staged runtime 中 `require('better-sqlite3')` 成功；已安装客户端健康检查 DB reachable。

### HW-TC-P17 值守 Agent 使用记忆辅助判断（2.1.30）

- **前置**：Worker 与值守 Agent 已绑定，Bridge 在线；Edge 本地记忆库包含与当前等待确认相关的 SOP 片段。
- **步骤**：Worker 进入等待用户确认状态，中心评估 binding 并调用值守 judge。
- **预期**：中心向 Edge 发送 `memory_search_request`；judge prompt 包含 `值守记忆检索` 区块；`human_watch_events.context_json.steward_memory_context` 写入检索摘要；最终仍通过 `session_continue` 写回 Worker。

### HW-TC-P18 值守 Agent 连续相同短回复仍可代发（2.1.31）

- **前置**：Worker 与 Codex 值守 Agent 已绑定，值守 Agent 上一轮已经输出过“继续”。
- **步骤**：Worker 再次进入等待确认状态，值守 Agent judge 再次输出“继续”。
- **预期**：Edge 按新增 assistant 消息识别该回复为新 judge reply；中心不再记录 `steward_judge_failed / Judge session returned empty reply`，而是进入 `intervention_attempt` 和 `intervention_completed=success`。
- **自动化**：`mission-control-client/src/lib/__tests__/human-watch-judge.test.ts`

### HW-TC-P19 值守 Judge 长耗时与重复请求保护（2.1.32）

- **前置**：Worker 与值守 Agent 已绑定，Edge Bridge 在线；值守 Agent 本地 CLI 响应可能超过 180 秒。
- **步骤**：触发 Worker 等待确认；在第一轮 Judge 未完成时，中心下一次 60 秒轮询再次命中同一 binding。
- **预期**：第一轮 Judge 允许最多 10 分钟完成；中心等待窗口为 11 分钟；重复 Judge 请求不会在 Edge 队列堆积，而是快速返回 `Steward judge already running for this agent`；Bridge 长耗时期间不因 90 秒心跳窗口误断。
- **自动化**：`mission-control-client/src/lib/__tests__/human-watch-judge.test.ts`、`mission-control/src/lib/__tests__/human-watch-orchestrator.test.ts`

### HW-TC-P20 值守 Judge 重复短回复时间戳识别（2.1.33）

- **前置**：Worker 与 Codex 值守 Agent 已绑定；值守 Agent 最近 assistant 文本已是 `继续`；会话足够长，固定分页内 assistant 数量可能不随新消息增加。
- **步骤**：再次触发 Worker 等待确认，值守 Agent 再次输出 `继续`。
- **预期**：Edge 以最新 assistant timestamp 晚于基线判定为新增回复，返回 `reply=继续`；中心进入 `intervention_attempt` 与 `intervention_completed=success`，不得记录 `Judge session returned empty reply`。
- **自动化**：`mission-control-client/src/lib/__tests__/human-watch-judge.test.ts`

### HW-TC-P21 值守绑定持久化 Worker 会话类型（2.1.35）

- **前置**：Worker 与值守 Agent 已绑定，Worker framework 为 `codex-cli`，Bridge 索引包含 `session_key`。
- **步骤**：创建或同步 Human Watch binding；随后触发 Worker transcript 评估。
- **预期**：`human_watch_bindings.worker_session_kind=codex-cli`；Bridge session 同步同时更新 `worker_session_id` 和 `worker_session_kind`；编排器创建 watch event 时上下文包含 `session_kind=codex-cli`，不得记录 `skip_reason=no_session_kind`。
- **自动化**：`mission-control/src/lib/__tests__/human-watch-binding-session-sync.test.ts`、`mission-control/src/lib/__tests__/human-watch-orchestrator.test.ts`

### HW-TC-P22 Edge 新建值守 Agent 默认额度（2.1.36）

- **前置**：从 Edge Web runtime 创建新的 Human Watch steward agent。
- **步骤**：读取新 Agent 的 `config.steward.binding_defaults` 和 `config.steward.rules`。
- **预期**：`binding_defaults.max_interventions_per_hour=60`，`binding_defaults.max_interventions_window_seconds=86400`；`rules` 中不包含节流额度字段，避免被误当作 transcript 匹配规则。
- **自动化**：`mission-control-client/src/lib/__tests__/human-watch-steward.test.ts`

### HW-TC-P23 确认类等待按内容去重（2.1.36）

- **前置**：两条 Worker assistant 消息都命中 `confirmation_text + idle_timeout`，但实际确认内容不同。
- **步骤**：分别调用规则评估，比较 `rulesHit.confirmation_text_hash` 和 `fingerprint`。
- **预期**：两次规则均命中；`confirmation_text_hash` 存在且不同；`fingerprint` 不同，后续编排器不得把新确认问题误判为 `fingerprint_duplicate`。
- **自动化**：`mission-control/src/lib/__tests__/human-watch-rules.test.ts`

### HW-TC-P24 值守 Judge 运行时错误不得代发（2.1.37）

- **前置**：Worker 与 Codex 值守 Agent 已绑定，Edge Bridge 在线；值守 Agent 本地 CLI 返回模型环境变量缺失、认证失败、API 错误或命令失败文本。
- **步骤**：Worker 进入等待确认状态，中心评估 binding 并调用值守 judge。
- **预期**：Edge 抛出 `Judge session returned runtime error`；中心写入 `human_watch_interventions(event_type=intervention_skipped, skip_reason=steward_judge_failed)`；不得创建自动代发成功事件，也不得把错误文本通过 `session_continue` 发给 Worker。
- **自动化**：`mission-control-client/src/lib/__tests__/human-watch-judge.test.ts`

### HW-TC-P25 Edge Bridge bootstrap 重复写入不重连（2.1.39）

- **前置**：Edge runtime 已连接生产中心，托盘周期性调用 `/api/edge/apply-bootstrap` 或 `/api/edge/import-tray-config`。
- **步骤**：重复写入相同 `gateway.server_url`、`gateway.token`、`device.client_id`，并改变 `edge.enrolled_at`。
- **预期**：设置照常落库；审计 `bridge_reconnect=false`；本地日志不出现对应的 `Bridge stopped / Starting remote server bridge`；生产中心可通过 Bridge 获取 Worker transcript。
- **自动化**：`mission-control-client/src/lib/__tests__/edge-bootstrap-settings.test.ts`

### HW-TC-P26 值守 5 秒触发并内容化回复（2.1.40）

- **前置**：Worker 与值守 Agent 已绑定，Bridge 在线；租户规则为 `idle_timeout_seconds=5`、`idle_timeout_with_stuck_seconds=5`、`grace_after_prompt_seconds=0`。
- **步骤**：Worker 提出需要用户回复的问题，并包含 `回答后说"确认"` 或 `回复后说"确认"`。
- **预期**：编排器在约 5 秒空闲后进入值守 judge；值守回复必须先回答 Worker 的实际问题，并在末尾包含确认词；不得只回复 `确认`、`继续` 或 `继续下一个问题`。
- **自动化**：`mission-control/src/lib/__tests__/human-watch-orchestrator.test.ts`、`mission-control/src/lib/__tests__/human-watch-judge.test.ts`

### HW-TC-P27 值守绑定自动停止（2.1.40）

- **前置**：binding 启用 `rules_override.auto_stop.enabled=true`，并配置 `max_successful_interventions=1` 或短 `max_runtime_seconds`。
- **步骤**：触发一次成功值守代发，或等待运行时长达到配置阈值。
- **预期**：当前 binding 被自动禁用；`human_watch_interventions` 写入 `event_type=auto_stop`，`decision=disabled`，`outcome=success`；其他 binding 不受影响。

### HW-TC-P28 自动停止后重新启用（2.1.59）

- **前置**：binding 首次创建时间已超过 `max_runtime_seconds`，随后通过 PATCH 重新启用。
- **步骤**：立即执行一次值守评估。
- **预期**：binding 保持启用并读取 Worker transcript；运行时长从本次启用时间重新计算，不产生新的 `auto_stop`。
- **自动化**：`mission-control/src/lib/__tests__/human-watch-orchestrator.test.ts`

### G19 关系表双重隔离与干净构建

1. 创建 metadata 为 `{}` 但存在 `supervision_goal_tasks` 关系的 inbox/assigned/in_progress/review 任务。
2. 执行 auto-route、assigned dispatch、stale requeue、Aegis 和 `/api/tasks/queue`，所有任务状态与分配必须不变。
3. Docker 与 Edge Runtime 构建日志必须显示在 `next build` 前删除 `.next`，发布镜像中 scheduler chunk 必须同时包含 metadata 和关系表排除条件。

### G20 Worker mailbox MCP 注入与调度最终拒绝

1. 中心监督消息 payload 必须包含 `worker_local_agent_id`，Edge mailbox 调用 Codex resume 时 argv 必须包含临时 `mcp_servers.mission_control` 配置，环境身份为对应 Worker/session。
2. Worker 必须真实调用 `mc_get_supervision_goal` 和 `mc_complete_supervision_task`；缺少工具时必须阻塞，不得伪造完成。
3. 即使 legacy 候选查询异常返回监督任务，mutation 前最终拒绝也必须保持其状态不变，且不得产生 `task_auto_routed`、`task_dispatched` 或 OpenClaw 活动。

### G21 结构性 hold 与 MCP annotations

1. 初次 dispatch 必须在同一事务内为依赖未完成任务写入 `__supervision_dependency_hold__`，使只检查 `assigned_to IS NULL` 的 legacy mutation 也无法更改任务。
2. 前置任务完成后，supervision monitor 必须在一次 dispatcher 事务中释放 hold 并立即分派后继任务，重复 tick 不得重复建任务或消息。
3. MCP `tools/list` 必须返回准确 annotations；以 `approval_policy=never` 运行的真实 Codex exec 必须能调用读取和非破坏性完成工具，不得返回 `user cancelled MCP tool call`。

### G22 紧凑 Goal 快照与调度权属竞态

1. 构造至少 50KB metadata/evidence/action 的 Goal，Worker Goal schema 2 响应必须保留所有任务状态和依赖，响应体小于 15KB，原始大字段不得返回。
2. 只保留 `created_by=goal-supervisor`、故意移除 metadata 和关系表信号时，stale requeue 和 assigned dispatch 仍必须跳过。
3. 普通任务被 legacy claim 后、OpenClaw 返回前新增 Goal 关系，失败写回必须被丢弃，不增加 `dispatch_attempts`、不改为 assigned/failed。
4. MCP `mc_get_task` 必须具有 read-only/non-destructive/idempotent/closed-world annotations。

### G23 受管值守续话非交互授权

1. Server 与 Edge MCP `tools/list` 必须为 `mc_continue_session` 返回 `readOnlyHint=false`、`destructiveHint=false`、`idempotentHint=true`、`openWorldHint=false`。
2. 在 `approval_policy=never` 的真实值守监督会话中调用该工具，不得返回 `user cancelled MCP tool call`；中心必须创建或幂等复用 `session.continue.requested`。
3. 相同 session 与相同 prompt 重试不得重复注入 Worker；不同 prompt 仍生成新的可靠消息。
4. 生产验收必须看到 Worker 真实命令输出、`mc_complete_supervision_task ok=true`、后继自动激活和最终独立验收，不得只以 MCP 工具被批准作为通过。

### G24 受管身份跨续话继承

1. 受管 MCP 发起同 session 续话后，下一轮启动参数必须继续包含临时 `mission_control` MCP、Worker ID 和 session ID。
2. 浏览器 cookie 请求即使伪造隐藏字段也不得获得 managedByPlatform；API-key 请求的 worker session 与目标 session 不一致时同样拒绝继承。
3. `mc_list_sessions` 和 `mc_session_transcript` 必须可在 approval never 下只读调用；`mc_control_session` 的 terminate/pause 仍需原审批。
4. 恢复生产 Goal 后，task 30 必须真实执行 `pwd` 并返回完成证据，不能只返回续话 accepted。

### G25 Correction/retry 消息 Worker 身份

1. 对已绑定 Worker/session 的监督任务执行 `retry_task` 或 `correct_direction`。
2. 生成的 `session.continue.requested` 必须在 payload 同时包含 `session_id`、`session_kind` 和 `worker_local_agent_id`，不得只依赖 `agent_ref`。
3. Edge mailbox ack 后的 Codex 进程环境必须包含 `MC_AGENT_ID`、`MC_WORKER_SESSION_ID` 和 `MC_SESSION_KIND`，且仍恢复原 session。
4. Worker 必须严格按 `mc_get_supervision_goal` → 任务命令 → `mc_complete_supervision_task` 提交，不得将 accepted/acked 当作任务完成。

### G26 有界 Goal 读取与终态纠偏

1. 向 Goal 写入至少 30 条长原因事件，Worker API 必须返回 schema 3、完整 `by_type` 计数、最近 20 条事件和 `history_windowed=true`。
2. 序列化响应必须小于 10KB，且不得包含 metadata、evidence_json 或 action_json 大字段。
3. `done` 任务存在旧 `worker_output_insufficient` 事件时，自动 Correction Engine 不得创建续话消息。
4. 生产发布前后必须检查 `mission-control.db` 文件描述符只属于当前容器；发现第二个持有者即失败。

### G27 Mailbox 恢复项目目录

1. 为 Worker Agent 配置已存在的 `mc_session_project_path`，调用 `enqueueLocalSessionPrompt` 时只传 `{ agent: { id } }`。
2. 执行器必须从本地数据库刷新完整 Agent 记录，并以持久化目录作为 `codex exec resume` 的 cwd。
3. 生产 Goal 的唯一 `pwd` 命令必须返回配置目录；失败时必须提交真实 failed 证据，后继任务不得激活。

### G28 受管完成事件验收证据

1. 仅有 task resolution、自报 success 且无平台事件时，Verifier 必须返回 `needs_human`。
2. 存在经中心 Worker/session/状态校验写入的 `goal_task_worker_completed` 时，Verifier 必须生成 `managed-completion` 独立证据引用并包含结构化 evidence。
3. Verifier accepted 时每条成功标准仍必须引用合法独立证据；伪造引用必须降级为人工确认。

### G29 分发沙箱与 strict Workspace

1. Agent 工具 `Read,Write` 与 Goal/Task 工具 `Read,Bash` 的有效集合必须为 `Read`；空交集直接拒绝，不得退化为不限制。
2. 单任务预算取 Agent 与 Goal/Task 最小值；cwd 必须 realpath 后仍在 Agent workspace，目录穿越和软链接逃逸均拒绝。
3. 两个 Workspace、两个 Edge 使用相同 local agent/session 形状时，只允许 `sync_clients + sync_agent_index + sync_sessions` 与当前 Workspace 完整匹配的一侧读取 transcript、continue、ack 和创建权限请求。
4. strict Workspace 必须拒绝无归属本机会话和网关会话，但不得阻断完整归属的 Human Watch Worker 与 Goal Supervisor Worker。
5. 真实值守验证必须看到 Worker 等待问句、`intervention_completed success`、Edge message ack 和同一 Worker transcript 中的值守语义回复，不接受仅创建队列消息作为通过。

### G32 Agent Inventory 实时同步与去重

1. Edge 新建一个普通 Agent 或值守 Agent 后，不重启 Bridge；中心应在实时事件到达后显示一次同名 Agent，并保留正确 `client_id/local_agent_id`。
2. Edge 修改、删除 Agent 后，中心索引应通过实时 `agent_status` 收敛；模拟 WebSocket 丢包时，下一次 HTTP heartbeat inventory 必须完成兜底更新。
3. 生产中心必须返回 `centralMode=true`，不得展示本地同步/添加普通 Agent 入口。
4. 数据库同时存在精确匹配的 `source=bridge` 遗留行和 `sync_agent_index` 行时，API 只返回索引 Agent；清理只能删除同 Workspace、同 Client、同 remote name 的遗留行。

### G33 可靠执行状态与监督过程

1. Mailbox 续写 CLI 成功前 inbox 必须保持 processing；CLI 抛错后本地 outbox 必须生成 fail，中心消息不得成为 completed。
2. 两个无依赖任务同时就绪且候选索引共享同一 `client_id + session_id` 时，只能激活一个，另一个保持等待且不创建第二条执行消息。
3. 监督任务详情必须返回 session/client/kind/updated_at；点击“查看过程”后从远程 transcript 读取真实 Worker 会话，并在活动状态下每 5 秒刷新。
4. transcript 没有任务派发后的新时间戳时，UI 必须提示“可能仍在排队或派发失败”，不能只显示执行中。

### G34 Runtime 兜底安装不破坏当前版本

1. 本机 standalone 缺少必需 Next compiled 文件时，fallback 候选校验必须失败，当前 Runtime 目录及其标记保持不变。
2. 在线下载候选已原子启用且版本完整时，后续配置持久化错误不得触发 standalone fallback 覆盖。
3. 发布 ZIP 必须在干净临时目录解压，确认 `app-route-turbo.runtime.prod.js` 等文件，并真实启动后由健康接口返回目标版本。
4. 安装升级后 `5101` 健康、Bridge 在线；恢复灰度任务后只能激活一个 Worker，同一 transcript 出现新任务轮次，CLI 完成后中心消息才能 completed。
5. 并发触发初始化、安装完成和周期恢复时只能存在一个 `5101` 监听者，重启后的 Node 日志不得新增 `EADDRINUSE`。
6. 安装前存在 KeepAlive 旧 LaunchAgent 时，3.0.10 启动后 launchd 中不再有该 job，plist 和过期 PID 被清理，但 Edge 配置与数据库保留。

### G35 Goal Worker 长任务执行窗口

1. 初次 Goal dispatch 和 `retry_task` / `correct_direction` 的可靠消息 payload 均必须包含 `execution_timeout_ms=1800000`。
2. Edge 收到 24 小时等过大值时，传入 CLI 的 `timeoutMs` 必须夹紧为 7200000 毫秒；未携带字段时仍使用本地 180000 毫秒默认。
3. 复杂真实 Worker 轮次运行超过 180 秒时，本地 inbox 和中心 message 必须仍保持 processing/leased，transcript 必须有分派后的新时间戳。
4. CLI 返回后才允许 completed/ACK；CLI 异常或 30 分钟超时必须 failed/fail，不得写入假完成。

### G36 Docker Runtime ZIP 一致性

1. `.dockerignore` 必须精确放行当前版本 Runtime ZIP，不得只放行历史版本。
2. release-surface 校验必须同时验证放行规则、manifest URL/SHA、本地 ZIP 存在性及 `.next/static/chunks`。
3. 镜像部署后公网 ZIP URL 必须返回 ZIP 而非 HTML，下载 SHA 必须与 manifest 完全一致。

### G37 阻塞 Goal 重试恢复

1. Goal 处于 `blocked`、Worker task 处于 `in_progress` 时执行 `retry_task`，Goal 必须在创建 Worker 消息前恢复为 `running`。
2. 同一事务必须写入 `goal_status_changed`，事件 `actor_type=steward_agent`且 `decision=resume`。
3. 恢复后 Worker 调用 `mc_complete_supervision_task` 必须返回 `ok=true`；任务转 `done/success` 后可靠消息才能 ACK `completed`。

### HW-TC-P29 自动代答可靠 mailbox 与 ACK 边界（2.1.84）

1. 规则命中并完成 judge 后，中心必须创建唯一 `session.continue.requested`，attempt 包含 `message_id/correlation_id`，此时不得提前存在 success completed。
2. Edge 完成原 Worker 会话续写后 ACK；中心才写 `intervention_completed/outcome=success`，并将 watch event 置为 resolved。
3. 相同 binding/session/fingerprint 重复评估必须复用同一消息；dead-letter 必须记录 failed completed。
