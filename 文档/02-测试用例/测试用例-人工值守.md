## 2. 干预留痕（关键）

### HW-TC-A01 代发成功留痕

- **前置**：租户已开通；binding 启用；Bridge 在线；规则可命中。
- **步骤**：触发编排代发 → continue 成功。
- **预期**：`human_watch_interventions` 含 `intervention_attempt` + `intervention_completed`（`outcome=success`）；`prompt_preview` 非空；`fingerprint` 一致。

### HW-TC-A02 代发失败留痕

- **前置**：模拟 Bridge continue 返回错误。
- **预期**：`intervention_completed` 且 `outcome=failed`；`error_message` 有值；**无** success 记录。

### HW-TC-A03 指纹去重跳过留痕

- **前置**：同 fingerprint 已成功代发过一次。
- **预期**：`intervention_skipped`，`reason=fingerprint_duplicate`；不发起第二次 continue。

### HW-TC-A04 Bridge 离线跳过留痕

- **前置**：client 离线。
- **预期**：`intervention_skipped`，`reason=bridge_offline`；无 `intervention_completed` success。

### HW-TC-A05 查询 API 租户隔离

- **步骤**：租户 A 写入；租户 B 调用 `GET /api/human-watch/interventions`。
- **预期**：B 看不到 A 记录。

### HW-TC-A06 Worker 详情 UI

- **步骤**：打开 Worker 详情「干预记录」。
- **预期**：最近 20 条倒序；含时间、结果、规则摘要。

### HW-TC-A07 连续确认值守容量

- **前置**：binding 为 `auto_send`；租户规则使用默认 `max_interventions_per_hour=60` 且 `max_interventions_window_seconds=86400`；Worker 连续提出多轮等待确认问题。
- **步骤**：连续触发 7 次以上不同 fingerprint 的等待确认。
- **预期**：第 7 次及后续不同问题仍可由值守 Agent 判官生成回复并通过 MCP/Bridge 发送；24 小时内超过默认上限才触发 `rate_limited`。

## 4. 权限请求与选项决策（V1.4）

### HW-TC-P01 创建权限请求

- **前置**：用户具备 operator 权限。
- **步骤**：调用 `POST /api/permission-requests`，传入 `request_type`、`title`、`prompt`、`risk`、两个以上 `options`。
- **预期**：返回 201；DB 中 `permission_requests.status=pending`；广播 `permission.requested`。

### HW-TC-P02 值守 Agent 按选项批准低/中风险

- **前置**：存在 `risk=medium` 的 pending 请求。
- **步骤**：调用 `POST /api/permission-requests/{id}/decision`，`deciderType=steward_agent`，`optionId` 指向 `action=approve` 的选项。
- **预期**：请求状态变为 `approved`；写入 `permission_request_decisions`；广播 `permission.decided`。

### HW-TC-P03 非法选项拒绝

- **步骤**：对 pending 请求提交不存在的 `optionId`。
- **预期**：400；请求仍为 `pending`；不写决策记录。

### HW-TC-P04 重复决策拒绝

- **步骤**：同一请求先批准，再提交第二次决策。
- **预期**：409/400；状态保持第一次结果；只保留一次有效决策。

### HW-TC-P05 过期请求不可决策

- **前置**：`expires_at` 小于当前时间。
- **步骤**：提交决策。
- **预期**：请求状态变为 `expired`；返回错误；不批准。

### HW-TC-P06 值守 Agent 不可批准高危请求

- **前置**：存在 `risk=high` 或 `critical` 的 pending 请求。
- **步骤**：`deciderType=steward_agent` 选择 `action=approve`。
- **预期**：403；请求仍 pending；可选择拒绝或转人工。

### HW-TC-P07 普通回复不改变权限状态

- **步骤**：值守 Agent 只通过聊天回复“同意”。
- **预期**：`permission_requests.status` 不变化；Worker 不应恢复执行，除非调用专门决策 API/MCP。

### HW-TC-P08 看门狗不误判等待审批的任务（2.1.17）

- **前置**：任务 `in_progress` 超过 10 分钟，对应 agent 存在 `permission_requests.status='pending'`。
- **步骤**：运行 `requeueStaleTasks()`。
- **预期**：任务状态保持 `in_progress`，不进入 `assigned`/`failed`；返回消息包含 "awaiting human approval" 计数。对照用例：agent 离线且无 pending 审批时仍正常 requeue。
- **自动化**：`mission-control/src/lib/__tests__/task-dispatch-stale.test.ts`

### HW-TC-P09 风险判断统一由值守侧规则裁定（2.1.17）

- **步骤**：创建 `permission_request`，worker 传入与实际内容不符的 `risk` 值。
- **预期**：`human_watch_events.priority` 由 `isDangerousPermissionRequest()` 规则结果决定，不直接采用 worker 自报的 `risk`。
- **自动化**：`mission-control/src/lib/__tests__/permission-requests.test.ts`

### HW-TC-P10 judge 建议采纳/驳回审计（2.1.17）

- **步骤**：人工 resolve 一个事件，分别测试 resolved_action 与 judge 原始 suggested_action 相同/不同两种情况；另测 system 自动 resolve 不应记录该审计。
- **预期**：`context.event_audit` 出现 `judge_suggestion_outcome`，`accepted` 字段正确反映是否一致；system 来源不产生该记录。
- **自动化**：`mission-control/src/lib/__tests__/human-watch-judge-feedback.test.ts`

### HW-TC-P11 高优先级事件接入 webhook（2.1.17）

- **步骤**：账号配置 webhook 订阅 `human_watch.event.high`；触发 `priority=high` 和 `priority=medium` 两种 `human_watch.event`。
- **预期**：`high` 触发额外的 `human_watch.event.high` 投递；`medium` 不触发该订阅的 webhook。
- **自动化**：`mission-control/src/lib/__tests__/webhooks-human-watch.test.ts`

### HW-TC-P12 Worker 主动求助触发值守回复（2.1.18）

- **前置**：Worker 与值守 Agent 已绑定，Bridge 在线，binding 为 `auto_send`。
- **步骤**：Worker 调用 `mc_create_watch_event`，只传 `prompt`，不传 `options`。
- **预期**：平台调用 `/api/human-watch/assist`；创建 `human_watch_events(source=worker_tool)`；调用值守 judge；通过 `session_continue` 把值守回复写回 Worker 会话；写入 `intervention_attempt` 与 `intervention_completed`。
- **自动化**：`mission-control/src/lib/__tests__/human-watch-orchestrator.test.ts`、`mission-control/src/lib/__tests__/codex-mcp-injection.test.ts`

### HW-TC-P13 Worker 等待用户回复话术命中规则（2.1.18）

- **步骤**：Worker 最后一条 assistant 消息包含“你希望/哪个/还是/是否/?”等等待用户回复语义，且超过空闲阈值。
- **预期**：`evaluateHumanWatchRules()` 命中 `awaiting_user_response` 与 `idle_timeout`。
- **自动化**：`mission-control/src/lib/__tests__/human-watch-rules.test.ts`

### HW-TC-P14 人工值守可靠 mailbox 离线排队与恢复（2.1.19）

- **前置**：开启 `MC_RELIABLE_EDGE_MESSAGES=1`，Worker 与值守 Agent 已绑定，Edge 支持 `reliable_mailbox` capability。
- **步骤**：Edge 离线时调用 `/api/human-watch/assist?delivery_mode=auto` 或 `queue_if_offline=true`；随后恢复 Edge，并触发 `/api/local/mailbox/drain`。
- **预期**：云端返回 `queued=true` 与 `message_id/correlation_id`；消息进入 `edge_messages(pending)`；本地上线后 lease 消息、调用值守 judge、继续写回 Worker session，并 ack 云端。
- **自动化**：`mission-control/src/lib/__tests__/human-watch-assist-route.test.ts`、`mission-control-client/src/lib/__tests__/local-mailbox-human-watch-assist.test.ts`

### HW-TC-P15 历史值守 Agent 自动创建 judge session（2.1.20）

- **前置**：Worker 与值守 Agent 已绑定，值守 Agent 是历史数据且 `session_key` 为空。
- **步骤**：云端投递 `human_watch.assist.requested`，本地 Mailbox drain 后执行值守 judge。
- **预期**：本地 runtime 自动 provision dedicated judge session，取得值守回复，随后把回复继续写入 Worker session；不再返回 `Steward has no dedicated judge session yet`。
- **自动化**：`mission-control-client/src/lib/__tests__/human-watch-judge.test.ts`、`mission-control-client/src/lib/__tests__/local-mailbox-human-watch-assist.test.ts`

### HW-TC-P16 Edge runtime native ABI 校验（2.1.20）

- **步骤**：执行 Edge runtime 打包脚本。
- **预期**：打包前 `pnpm rebuild better-sqlite3` 成功；staged runtime 中 `require('better-sqlite3')` 成功；已安装客户端健康检查 DB reachable。
- **自动化**：`mission-control-client/scripts/package-edge-runtime.sh`

### HW-TC-P17 值守 Agent 使用记忆辅助判断（2.1.30）

- **前置**：Worker 与值守 Agent 已绑定，Bridge 在线；Edge 本地记忆库包含与当前等待确认相关的 SOP 片段。
- **步骤**：Worker 进入等待用户确认状态，中心评估 binding 并调用值守 judge。
- **预期**：中心向 Edge 发送 `memory_search_request`；judge prompt 包含 `值守记忆检索` 区块；`human_watch_events.context_json.steward_memory_context` 写入检索摘要；最终仍通过 `session_continue` 写回 Worker。
- **自动化**：`mission-control/src/lib/__tests__/human-watch-orchestrator.test.ts`、`mission-control-client/src/lib/__tests__/memory-sync-search.test.ts`

### HW-TC-P18 值守 Agent 连续相同短回复仍可代发（2.1.31）

- **前置**：Worker 与 Codex 值守 Agent 已绑定，值守 Agent 上一轮已经输出过“继续”。
- **步骤**：Worker 再次进入等待确认状态，值守 Agent judge 再次输出“继续”。
- **预期**：Edge 按新增 assistant 消息识别该回复为新 judge reply；中心不再记录 `steward_judge_failed / Judge session returned empty reply`，而是进入 `intervention_attempt` 和 `intervention_completed=success`。
- **自动化**：`mission-control-client/src/lib/__tests__/human-watch-judge.test.ts`
