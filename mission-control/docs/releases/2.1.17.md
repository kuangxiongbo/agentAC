# AgentCenter 2.1.17 Release Notes

Date: 2026-06-21

## Changes

- Task dispatch no longer mistakes a worker that is legitimately blocked on a pending human-watch permission request for a dead/stuck session: `requeueStaleTasks()` now checks for a pending `permission_requests` row for the assigned agent before requeueing or failing a stale `in_progress` task.
- Risk classification for permission requests / human-watch events is now judged centrally against the existing predefined dangerous-action rule set (`isDangerousPermissionRequest`), instead of trusting whatever `risk` value the worker self-reported. Worker-reported risk is no longer used to set notification priority.
- Human-watch judge suggestion feedback: when a human resolves a human-watch event, the system now records whether the resolution matched the judge's original suggestion (`judge_suggestion_outcome` audit entry with `accepted: true/false`). System/steward auto-resolutions are not counted, only human decisions — a passive data point for a future acceptance-rate report, no behavior change.
- High-priority (`high`/`critical`) human-watch events and permission-request events are now wired into the existing webhook delivery system (`human_watch.event`, `human_watch.event.high`, `permission.requested`, `permission.decided`). Accounts with a webhook configured for `human_watch.event.high` are notified even if nobody is watching the dashboard. `fireWebhooksAsync` now batches multiple derived event types into a single DB query per broadcast event.
- Publishes Edge Web runtime `2.1.17`; tray native app remains `3.0.6`.

## Upgrade Notes

- Installed users do not need a new tray native build for this release; tray remains `3.0.6`.
- Operators who want a proactive ping for high-risk human-watch events should add a webhook subscribed to `human_watch.event.high` (or `*`) in Webhooks settings — this is opt-in, no existing webhook subscriptions are affected.
- No DB migration required; the judge-feedback audit entry and risk-classification change are purely additive to the existing `context_json` / `priority` fields.

## Known Risks

- The human-watch judge feedback loop only records acceptance/override; there is no report UI yet to surface the acceptance rate.
- `human_watch.event.high` webhook delivery has not been verified against a real external endpoint (Slack/WeCom) in production, only via mocked `fetch` in unit tests.
- Intel tray/runtime artifacts are still not published in production manifests yet.
