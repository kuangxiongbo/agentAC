# 2.1.40 - Human Watch Fast Stewarding

Date: 2026-07-08

## User / Operator Changes

- Human Watch can now be configured down to a 5 second idle threshold for small-scope unattended validation.
- The default Human Watch global rules use `idle_timeout_seconds=5`, `idle_timeout_with_stuck_seconds=5`, and `grace_after_prompt_seconds=0`.
- Explicit prompts such as `回答后说"确认"` / `回复后说"确认"` are classified as answer-required waits: the steward judge must answer the actual question first, then include confirmation.
- All Human Watch responses still go through the steward Agent judge and memory context so the reply is based on the Worker question instead of a fixed template.
- Human Watch bindings now support per-binding automatic stop rules to prevent unattended validation from running forever:
  `max_successful_interventions`, `max_runtime_seconds`, and `max_rate_limited_skips`.
- The Worker and steward binding controls expose automatic stop settings. When a stop condition is reached, the binding is disabled and an `auto_stop` intervention record is written.

## Data / API / Migration Notes

- No database migration.
- Existing tenant rules can be updated in place with `idle_timeout_seconds=5`, `idle_timeout_with_stuck_seconds=5`, and `grace_after_prompt_seconds=0`.
- The Human Watch rules UI now permits saving a 5 second idle threshold.
- `rules_override.auto_stop` is stored on existing Human Watch bindings. It is optional and backward compatible.
- `human_watch_interventions.event_type` can now contain `auto_stop` for audit-only automatic shutdown records.

## Gray Release Risks

- Human Watch calls the steward Agent judge, so end-to-end response time depends on local model/runtime latency after the 5 second trigger threshold.
- A 5 second threshold increases intervention frequency; keep the 24 hour max intervention window enabled for cost and loop control.
- Automatic stop disables only the binding that reaches its configured condition; operators should re-enable it intentionally for another validation run.
